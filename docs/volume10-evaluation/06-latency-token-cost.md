# Latency·Token·Cost 측정

## 1. 학습 목표

이 장을 완료하면 다음을 할 수 있어야 합니다.

- 지연 시간, 입력·출력 토큰, 비용을 품질 점수와 분리해 읽는다.
- 라이브 시계·모델 SDK 대신 검토한 고정 사용량 기록을 평가 계약으로 만든다.
- 토큰당 고정 마이크로 USD 단가로 비용을 부동 소수 가격표 없이 재현한다.
- 평균 latency와 nearest-rank P95가 다른 위험을 나타냄을 설명한다.
- 사례 ID·기록 완전성·단위 검증으로 선택 편향과 단위 오류를 막는다.

## 2. 왜 필요한가

답변 정확도와 작업 성공률이 높아도 응답이 느리거나 비용이 예산을 넘으면 운영 품질은 충분하지 않습니다. 반대로 평균 시간이 짧아도 소수의 느린 요청이 사용자 경험을 망칠 수 있습니다. 따라서 latency, token, cost를 별도 기준선으로 측정하고 품질 지표와 함께 비교합니다.

이 장은 성능 벤치마크가 아닙니다. CPU 부하, 네트워크, 모델 서버 상태에 따라 바뀌는 `time` 측정 대신, 검토 가능한 고정 밀리초·토큰 기록을 읽습니다. 그래서 코드·프롬프트·라우트 후보를 비교할 때 계산 계약과 숫자 해석을 먼저 안정시킬 수 있습니다.

> [!WARNING]
> 고정 기록의 비용은 실제 청구서나 최신 공급자 가격이 아닙니다. 고객 요청, API 키, 운영 사용량, 결제 정보, 라이브 모델을 사용하지 않습니다. 운영에서는 승인된 계측 이벤트와 가격 버전·통화·할인·재시도 정책을 별도로 보관해야 합니다.

## 3. 핵심 개념

- **Latency:** 한 사례에 기록된 끝단 간 지연 시간(ms)입니다. 이 실습에서는 벽시계로 재측정하지 않습니다.
- **Mean latency:** 모든 고정 latency의 산술 평균입니다. 다섯 사례의 합계 920ms를 5로 나눈 184.000000ms입니다.
- **P95 latency:** 정렬한 latency에서 `ceil(0.95 × n)`번째 값을 택하는 nearest-rank 백분위입니다. 다섯 사례에서는 340ms입니다.
- **Input / output token:** 고정 기록의 요청·응답 토큰 수입니다. 둘을 더한 값이 total token입니다.
- **Micro USD:** USD의 1/1,000,000 단위 정수입니다. 토큰 단가와 사례 비용을 정수로 계산해 이진 부동 소수 오차를 피합니다.
- **완전성:** 모든 골든 사례에 정확히 하나의 사용량 기록이 있어야 합니다. 빠르거나 싼 일부 사례만 골라 평균을 낼 수 없습니다.

## 4. 동작 구조

```text
버전 관리 GoldenDataset                 고정 사용량/단가 기록
(case_id 5개)                    (latency ms · input/output token · micro USD/token)
             │                                      │
             └──────────────────┬───────────────────┘
                                ▼
                 case_id 완전성 · 단위·범위 검증
                                ▼
                  UsageCaseMetrics (사례별 비용)
                                ▼
       Mean latency · nearest-rank P95 · token 합계 · cost 합계
                                ▼
                  같은 데이터셋·단가 버전에서 회귀 비교

LLM API · Agent 도구 · Vector DB · 네트워크 · 라이브 시계 · 난수 ── 사용하지 않음
```

`evaluate_usage_cases()`는 입력 사례 순서를 보존하면서 사례별 token·cost를 반환합니다. `evaluate_usage()`는 이 결과를 합산하고 P95를 계산합니다. P95 위치는 `ceil(95 × 사례 수 / 100) - 1`의 0-기반 인덱스로 정하므로 보간이나 현재 시스템 상태가 개입하지 않습니다.

## 5. 실습 환경

이 장에서 사용할 산출물은 다음과 같습니다.

- `src/ai_platform/evaluation/usage_metrics.py`: 사용량 입력 계약, 비용 계산, latency·token 집계를 정의합니다.
- `src/ai_platform/evaluation/datasets.py`: 골든 사례와 같은 ID의 고정 기록 및 마이크로 USD 단가를 정의합니다.
- `examples/volume10/usage_quality.py`: 전체 기준선을 출력합니다.
- `tests/evaluation/test_usage_metrics.py`: 수치, P95 규칙, 완전성, ID·단위 계약을 검사합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv sync --all-groups
```

환경 변수, API 키, 모델 서버, 네트워크 연결, 운영 계측기는 필요하지 않습니다. Windows Git Bash에서도 저장소 루트에서 같은 `uv` 명령을 실행할 수 있습니다.

## 6. 단계별 실습

### 6.1 고정 사용량 기준선 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run python examples/volume10/usage_quality.py
```

다섯 골든 사례의 평균·P95 latency, 총 token, 총 cost를 출력합니다. `benefits-enrollment`의 340ms는 가장 느린 기록이라 이 작은 표본의 P95를 결정합니다. 단, 이것은 실제 요청을 실행한 시간이 아니라 고정된 교육용 기록입니다.

### 6.2 계약 테스트 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/evaluation/test_usage_metrics.py -q
```

테스트는 기준 수치, 골든 데이터셋과의 동일 사례 ID, stable case 순서, nearest-rank P95, 누락 기록, 키/객체 ID 불일치, 음수·실수·불리언 측정값, 중복 사례를 검사합니다.

### 6.3 비용 단위를 해석하는 방법

고정 단가는 입력 token당 2 micro USD, 출력 token당 8 micro USD입니다. 예를 들어 `access-reset`은 입력 140개와 출력 90개이므로 `140 × 2 + 90 × 8 = 1,000` micro USD입니다. 총 5,240 micro USD는 `0.005240` USD로 표시합니다. 실제 제공자 가격이나 환율로 바꾸지 않습니다.

### 6.4 비교 조건 고정

후보 구현을 비교할 때는 `volume10-support-policy@1.0.0`, 같은 다섯 사례, 같은 단위(ms/token/micro USD), 같은 P95 정의, 같은 입력·출력 단가를 유지합니다. 사례나 가격 계약을 바꾸면 데이터셋·가격 버전과 변경 근거를 기록하고 이전 기준선과 직접 비교하지 않습니다.

## 7. 코드 설명

`RecordedUsage`는 `case_id`, 양의 정수 `latency_ms`, 0 이상 정수 `input_tokens`, `output_tokens`를 받습니다. `TokenPricing`은 토큰당 마이크로 USD 정수 단가를 받습니다. 불리언은 Python에서 정수의 하위형이지만 측정값으로는 허용하지 않아 SDK 직렬화 오류를 빠르게 드러냅니다.

`evaluate_usage_cases()`는 골든 사용량 사례와 기록 사전의 ID 집합이 완전히 같은지 검사합니다. 그리고 입력과 출력 token에 각각의 고정 단가를 곱해 사례 비용을 계산합니다. `evaluate_usage()`는 latency 합계·평균·P95, token 합계, 비용 합계를 계산합니다. 5개 같은 가중치 사례의 P95는 정렬된 `[70, 120, 180, 210, 340]`에서 다섯 번째인 340ms입니다.

비용은 정수 micro USD로 보관하고 표시 단계에서만 1,000,000으로 나눕니다. 이 선택은 소수점 반올림이 기준선의 분자·분모를 바꾸지 않게 합니다. 실제 비용은 모델별 계층 가격, 캐시, 실패 요청, 할인, 세금 같은 더 많은 계약이 필요하므로 이 교육용 합계와 동일시하지 않습니다.

## 8. 정상 실행 결과

6.1 명령은 다음 출력을 포함해야 합니다.

```text
Evaluation cases: 5
Mean latency (ms): 184.000000
P95 latency (ms): 340
Total tokens: 1240
Total cost (USD): 0.005240
```

평균 184ms는 다섯 기록의 합계를 사용하며 P95 340ms는 최대 기록을 사용합니다. 총 token 1,240은 입력 780과 출력 460의 합이며, 총 비용은 입력 `780 × 2`와 출력 `460 × 8` micro USD의 합입니다.

6.2 pytest 명령은 실행 시간과 무관하게 `passed`로 끝나야 합니다. 값이 다르면 현재 시계나 라이브 모델 호출로 맞추지 말고 고정 기록, 사례 ID, P95 규칙, 마이크로 USD 단가를 기준선과 비교합니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `recorded usage must match case ids` | 일부 사용량 기록이 빠졌거나 예상 밖 ID가 있다. | 모든 `UsageCase`에 정확히 하나의 기록을 제공한다. |
| `key and case_id must match` | 결과 사전 키와 기록 내부 ID가 다르다. | 동일한 안정된 `case_id`를 키와 객체에 사용한다. |
| `latency_ms must be a positive integer` | 0, 음수, 실수, 불리언이 들어갔다. | 경과 시간을 양의 정수 ms로 정규화하고 원시 단위는 별도 보관한다. |
| `must be a non-negative integer` | token 또는 micro USD 단가가 음수·실수·불리언이다. | 수를 정수 단위로 변환하고 음수 보정값은 별도 회계 계약으로 처리한다. |
| 평균은 낮지만 P95가 높다 | 일부 사례가 긴 tail latency를 가진다. | 가장 느린 사례·단계·재시도 원인을 별도 분석한다. |
| 비용이 낮아졌지만 품질이 하락한다 | token 절감이 답변·작업 성공을 손상시켰다. | 품질, 안전, 비용 지표를 함께 보고 단일 cost 점수로 승인하지 않는다. |

## 10. 응용 실습

1. 고정 사례 여섯 개를 설계하고 nearest-rank P95 위치를 손으로 계산한 뒤 테스트로 고정합니다.
2. 출력 token 단가만 두 배로 바꿨다고 가정하고 각 사례와 전체 비용이 어떻게 변하는지 계산합니다. 실제 가격 API는 호출하지 않습니다.
3. `benefits-enrollment`의 latency만 줄여 평균과 P95가 각각 언제 바뀌는지 설명합니다.
4. 실제 계측 이벤트에 trace ID, 모델 ID, 가격 버전, 재시도 횟수, 캐시 상태를 추가하는 스키마를 설계하되 실제 이벤트를 전송하지 않습니다.

## 11. 실무 적용

운영에서는 요청 시작·첫 토큰·마지막 토큰·도구 단계·최종 응답을 명확히 정의해 어떤 latency를 보고하는지 합의해야 합니다. 표본 수와 분포를 함께 보며 P50/P95/P99, 오류율, 재시도, 캐시 적중, 지역, 모델·프롬프트 버전별로 분해합니다. 수집 데이터에는 민감한 프롬프트 본문이나 비밀값을 넣지 않고 최소 수집·비식별화·보존·접근 통제를 적용합니다.

비용 계약에는 모델별 입력/출력·캐시·배치 단가, 통화, 가격 발효일, 반올림 정책, 실패·재시도 청구 여부를 버전과 함께 기록합니다. 회귀 리포트에는 코드 커밋, 골든 데이터셋 ID·버전, 사례 수, latency 분포, token 합계, 비용 합계, 답변·검색·작업 품질, 승인 임계값을 같이 남깁니다. 고비용·저품질 후보는 자동 배포가 아니라 검토 대상으로 보냅니다.

## 12. 과제

- **기본:** Mean latency와 P95가 서로 다른 문제를 드러내는 이유를 설명합니다.
- **응용:** micro USD 정수 단가를 쓰는 이유와 표시 단계에서 USD로 변환하는 위치를 설명합니다.
- **심화:** 실제 LLM 시스템의 스트리밍, 캐시, 도구 재시도, 환불, 모델별 가격 변경을 포함한 계측·비용 계약을 설계합니다. 개인정보 최소화, 데이터셋·가격 버전, 오류 처리, 품질 안전장치를 포함하며 라이브 API는 호출하지 않습니다.

## 14. 핵심 정리

Latency, token, cost는 답변·검색·Router·Agent 품질과 다른 축의 운영 신호입니다. 고정 사례 ID, 기록된 정수 ms/token, 고정 micro USD 단가, 완전성 검증, nearest-rank P95 규칙을 함께 고정하면 현재 환경이나 공급자 가격 변화 없이 비교 가능한 기준선을 얻습니다. 이 장의 수치는 교육용 기록이므로 실제 SLO·청구서가 아니며, 운영에서는 버전 관리된 계측·가격 계약과 안전·품질 지표를 함께 사용해야 합니다. 다음 장에서는 같은 고정 기준선을 후보 결과와 비교하는 회귀 리포트로 확장합니다.
