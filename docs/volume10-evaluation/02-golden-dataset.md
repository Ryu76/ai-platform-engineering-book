# Golden Dataset: 설계, 라벨, 버전 관리

## 1. 학습 목표

이 장을 완료하면 다음을 할 수 있어야 합니다.

- 골든 데이터셋과 단순 테스트 입력의 차이, 그리고 라벨 근거가 필요한 이유를 설명한다.
- 답변 가능(`answer`)과 답변 보류(`abstain`, no-answer) 사례를 명시적으로 구분한다.
- 사례 ID, 질의, 카테고리, 기대 동작, 정답 문서 ID, 라벨 근거, 출처 참조를 하나의 고정 계약으로 관리한다.
- 데이터셋 ID와 `MAJOR.MINOR.PATCH` 버전을 함께 기록해 비교 조건을 보존한다.
- 외부 서비스나 실제 고객 데이터 없이 고정 데이터셋 감사를 재현한다.
- 검색 Recall의 양성 사례와 no-answer 정확도 평가가 다른 지표라는 점을 설명한다.

## 2. 왜 필요한가

평가 데이터가 바뀌면 모델·Retriever·Prompt가 바뀌지 않아도 평균 점수가 달라집니다. 사례 목록만 저장하고 누가 어떤 근거로 라벨을 정했는지 남기지 않으면, 낮은 점수가 시스템 결함인지 라벨 오류인지 판단할 수 없습니다.

따라서 골든 데이터셋은 임시 샘플이 아니라 **검토된 비교 기준**입니다. 이 장은 `GoldenCase`에 기대 동작과 라벨 근거를 함께 고정하고, `GoldenDataset`에 명시적 버전을 부여합니다. 기본 경로는 코드에 포함된 공개용 정책 ID만 읽으며 API, 네트워크, 시계, 난수에 의존하지 않습니다.

> [!WARNING]
> 실제 고객 질의, 개인정보, 사내 문서 본문, API 키를 골든 데이터에 복사하지 마세요. 운영 로그를 후보로 쓸 때는 비식별화·접근 권한·보존 기간·검토 승인을 별도 절차로 관리합니다. 이 장의 사례와 출처 참조는 교육용 고정 식별자입니다.

## 3. 핵심 개념

- **골든 데이터셋:** 사람이 검토한 질의와 기대 결과의 버전 관리된 기준 집합입니다.
- **라벨 근거:** 왜 그 문서가 정답인지, 또는 왜 답변을 보류해야 하는지를 설명하는 짧은 검토 기록입니다.
- **출처 참조:** 라벨을 검토할 수 있게 하는 문서 ID·카탈로그 버전 등의 안정된 참조입니다.
- **`answer`:** 하나 이상의 관련 문서 ID가 있어야 하는 기대 동작입니다.
- **`abstain`:** 현재 평가 범위에 관련 문서가 없으므로 근거 없는 답변 대신 보류해야 하는 기대 동작입니다.
- **데이터셋 버전:** 동일 조건의 회귀 비교에 쓰는 `MAJOR.MINOR.PATCH` 식별자입니다. 라벨 의미를 깨는 변경은 major, 사례 추가는 minor, 오탈자·메타데이터 정정은 patch로 기록합니다.
- **고정 데이터:** 실행 중 다운로드·샘플링·수정하지 않는 입력입니다. 고정 데이터가 곧 좋은 데이터라는 뜻은 아니므로 대표성 검토를 함께 합니다.

## 4. 동작 구조

```text
고정 GoldenCase
(ID · 질의 · 카테고리 · 기대 동작 · 정답 · 근거 · 출처)
                              │
                              ▼
GoldenDataset
(dataset_id · MAJOR.MINOR.PATCH · 고유 사례 ID)
                              │
                              ▼
입력 계약 검증 ──► 중복 ID / 모순된 no-answer / 빈 근거는 실패
                              │
              ┌───────────────┴────────────────┐
              ▼                                ▼
      answer 사례                      abstain 사례
Retrieval Recall·MRR 등          보류 정확도·근거 없는 답변률 (후속 장)
              │                                │
              └─────────► 버전과 함께 리포트·회귀 비교
```

`FIXED_GOLDEN_DATASET`은 다섯 사례를 가진 `volume10-support-policy@1.0.0`입니다. 네 개는 검색 품질 지표에 쓰는 `answer` 사례이고, `office-parking` 한 개는 의도적으로 관련 문서가 없는 `abstain` 사례입니다. 현재 `evaluate_retrieval()`는 정답 문서가 있는 사례만 받습니다. no-answer를 0 Recall로 섞으면 "문서를 놓쳤다"와 "문서가 존재하지 않는다"를 혼동하기 때문입니다.

## 5. 실습 환경

다음 파일이 이 장의 고정 산출물입니다.

- `src/ai_platform/evaluation/golden_dataset.py`: 사례·데이터셋·버전·no-answer 입력 계약과 결정론적 요약을 정의합니다.
- `src/ai_platform/evaluation/datasets.py`: 공개용 `volume10-support-policy@1.0.0` 고정 사례와 검색용 양성 부분집합을 정의합니다.
- `examples/volume10/golden_dataset_audit.py`: 버전과 사례 구성을 사람이 읽을 수 있는 순서로 출력합니다.
- `tests/evaluation/test_golden_dataset.py`: 라벨 모순, 중복 ID, 잘못된 버전과 기준 요약을 검사합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv sync --all-groups
```

이 실습에는 환경 변수, API 키, 모델 서버, 벡터 데이터베이스가 필요하지 않습니다.

## 6. 단계별 실습

### 6.1 고정 데이터셋 구성 감사

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run python examples/volume10/golden_dataset_audit.py
```

출력에서 데이터셋 ID와 버전, 전체 사례 수 5, `answer` 4건, `abstain` 1건을 확인합니다. 카테고리는 코드의 입력 순서가 아니라 정렬된 이름으로 출력하므로 같은 소스에서는 항상 동일합니다.

### 6.2 라벨·버전 계약 테스트

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/evaluation/test_golden_dataset.py -q
```

테스트는 `answer`인데 정답 문서가 없거나 `abstain`인데 정답 문서가 있는 모순을 거부합니다. 또한 사례 ID 중복과 `MAJOR.MINOR.PATCH` 형식이 아닌 버전을 실패시킵니다.

### 6.3 변경을 비교 가능한 단위로 기록

사례를 추가하거나 라벨을 바꾸기 전에 기존 버전, 변경 이유, 라벨 검토자, 영향받는 사례 ID를 기록합니다. 시스템 코드 변경과 데이터셋 변경을 한 회귀 표에 섞지 않습니다. 같은 데이터셋 버전에서만 시스템 점수를 직접 비교합니다.

## 7. 코드 설명

`GoldenCase.__post_init__()`는 사람이 읽을 텍스트 필드, 정답 문서 ID의 중복, 기대 동작의 모순을 검사합니다. `GoldenDataset.__post_init__()`는 빈 데이터셋·중복 사례 ID·형식이 다른 버전을 거부합니다. 이 실패는 점수를 만들어 내는 대신 잘못된 비교 기준을 조기에 드러냅니다.

`summarize_golden_dataset()`은 사례 수, 기대 동작 수, 정렬된 카테고리 수만 집계합니다. 시간이나 외부 상태를 읽지 않으므로 감사 출력은 결정론적입니다. `FIXED_RETRIEVAL_CASES`는 `answer` 사례만 `RetrievalCase`로 변환합니다. 후속 답변 평가 장에서 `abstain` 사례에는 별도 보류 정확도와 근거 없는 답변률을 적용합니다.

## 8. 정상 실행 결과

6.1 명령은 다음 출력을 포함해야 합니다.

```text
Dataset: volume10-support-policy
Version: 1.0.0
Cases: 5
Answer cases: 4
Abstain cases: 1
Categories: facilities=1, finance=1, identity=1, people=1, security=1
```

6.2 명령은 pytest 버전에 따라 실행 시간은 달라도 `passed`로 끝나야 합니다. 버전이나 사례 수가 다르면 먼저 고정 데이터 변경 이력과 테스트 기대값을 확인합니다. 외부 데이터를 가져오거나 예상값만 바꿔서 해결하지 않습니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `answer cases must have at least one relevant document` | 답변 가능 라벨에 정답 문서가 없다. | 관련 문서 ID와 라벨 근거를 추가하거나 기대 동작을 `abstain`으로 재검토한다. |
| `abstain cases must not have relevant documents` | no-answer와 정답 문서를 동시에 선언했다. | 현재 범위에서 답변 가능한지 라벨 검토 후 둘 중 하나만 남긴다. |
| `golden dataset case ids must be unique` | 같은 사례가 두 번 있어 집계가 모호하다. | 안정된 고유 ID를 부여하고 중복 사례를 병합 또는 제거한다. |
| `version must use MAJOR.MINOR.PATCH format` | 비교 기준 버전이 불명확하다. | `1.0.0` 같은 세 정수 버전으로 변경 이유와 함께 기록한다. |
| 검색 지표 사례 수가 5가 아니라 4다 | `abstain`은 현재 검색 Recall 분모에서 제외된다. | 오류가 아니다. no-answer는 후속 답변 보류 지표에서 별도로 평가한다. |

## 10. 응용 실습

1. `answer` 사례를 하나 추가하고 새 카테고리와 라벨 근거·출처 참조를 작성합니다. 왜 `1.1.0`이 적절한지 설명합니다.
2. 기존 사례의 정답 문서를 변경해야 한다고 가정합니다. 라벨 오류 수정과 정책 의미 변경을 구분하고 각각 어떤 버전 증가가 필요한지 정합니다.
3. no-answer 사례에 모델이 답변을 생성한 결과를 기록한다고 가정합니다. 보류 성공, 근거 없는 답변, 검색 실패를 분리하는 혼동 행렬을 설계합니다. 라이브 모델을 호출하지 않습니다.

## 11. 실무 적용

실무 골든 데이터셋에는 사례 소유자, 생성·검토 날짜, 라벨 지침 버전, 출처 스냅샷, 대표성 층화, 민감도 등급을 별도 레지스트리로 관리합니다. 라벨은 최소 두 명의 검토와 불일치 해소 규칙을 두고, 검토자는 시스템 출력·실험 조건을 익명화한 뒤 판단합니다.

대표성은 평균만으로 보장되지 않습니다. 사용자 의도, 언어, 난이도, 최신성, 실패 이력, no-answer, 안전 제약별로 분포를 점검하고, 일부 집단의 사례가 적으면 전체 평균과 함께 구간별 점수를 보고합니다. 운영 데이터는 승인된 비식별화 파이프라인을 거친 뒤에만 후보가 될 수 있습니다.

> [!TIP]
> 평가 리포트에는 코드 커밋, 데이터셋 ID·버전, 사례 수와 제외 규칙, 지표 정의, 실패 사례 ID를 함께 남기세요. 데이터셋 버전이 다르면 "개선" 대신 서로 다른 기준에서 측정했다는 사실부터 보고합니다.

## 12. 과제

- **기본:** `answer`와 `abstain` 사례가 정답 문서 ID에 대해 각각 어떤 계약을 가져야 하는지 작성합니다.
- **응용:** 다섯 사례의 카테고리 분포가 실제 제품의 사용자 의도를 대표하는지 평가할 추가 정보를 나열합니다.
- **심화:** 개인정보를 노출하지 않는 라벨 검토 워크플로와 데이터셋 변경 승인 템플릿을 설계합니다. 실제 로그·비밀값·외부 API는 사용하지 않습니다.

## 14. 핵심 정리

골든 데이터셋은 점수의 분모를 정의하는 제품 계약입니다. 각 사례에 기대 동작, 정답, 라벨 근거, 출처 참조를 남기고 버전을 고정해야 변경 전후를 공정하게 비교할 수 있습니다. no-answer는 검색 실패가 아니라 보류해야 할 상황일 수 있으므로, 정답 문서가 있는 검색 지표와 별도의 답변 보류 평가로 분리합니다. 다음 장에서는 이 고정 기준으로 Recall, Precision, Hit Rate, MRR, NDCG의 트레이드오프를 더 깊게 해석합니다.
