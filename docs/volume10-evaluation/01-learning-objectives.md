# Evaluation: 학습 목표와 결정론적 평가 출발점

## 1. 학습 목표

이 장을 완료하면 다음을 할 수 있어야 합니다.

- 평가(Evaluation)가 기능 구현 뒤에 한 번 수행하는 행사가 아니라 변경 전후 품질을 비교하는 계약임을 설명한다.
- 골든 데이터셋(Golden Dataset), 테스트 사례(Test Case), 오프라인 평가(Offline Evaluation)의 역할을 구분한다.
- 검색 결과에서 Recall@k, Precision@k, Hit Rate@k, MRR(Mean Reciprocal Rank), NDCG@k를 계산하고 해석한다.
- 고정된 질의·정답 문서·순위 결과로 외부 의존성 없는 평가를 실행한다.
- 누락 사례, 중복 문서 순위, 잘못된 `k`를 평가 오류로 처리하는 이유를 설명한다.
- 모델 호출 결과와 평가 기준을 분리하여, 같은 입력에서 같은 측정 결과를 재현한다.

## 2. 왜 필요한가

RAG, Router, Agent, LLM 애플리케이션은 실행되었다는 사실만으로 품질이 보장되지 않습니다. 검색기가 관련 문서를 반환하지 못하면 근거 기반 답변을 생성하기 어렵고, Prompt나 색인 설정을 바꾼 뒤 품질이 좋아졌는지도 직감만으로 판단할 수 없습니다.

평가는 변경 가능한 시스템 결과를 고정된 기대값과 비교합니다. 먼저 작고 공개 가능한 골든 데이터셋에서 결정론적 지표를 만들면, 이후 Retriever·Router·Prompt를 변경할 때 회귀(regression)를 발견할 수 있습니다. 이 장의 평가는 LLM-as-a-Judge나 사람 평가를 대체하지 않습니다. 두 방식은 뒤에서 다루되, 비용·모델 편향·판정 변동이 없는 기준선을 먼저 만듭니다.

> [!WARNING]
> 평가 데이터에 실제 고객 질의, 개인정보, API 키, 비공개 문서를 넣지 마세요. 이 장의 데이터와 결과는 코드에 고정되어 있으며 네트워크와 API 키를 사용하지 않습니다. 실제 운영 로그를 평가에 사용할 때는 수집 목적, 보존 기간, 접근 권한, 비식별화 절차를 별도로 검토해야 합니다.

## 3. 핵심 개념

- **골든 데이터셋:** 질의와 정답 또는 기대 결과를 사람이 검토해 고정한 기준 데이터입니다. 모델 출력 자체가 아니라 평가의 기준을 버전 관리합니다.
- **오프라인 평가:** 배포 전 또는 CI에서 기록된 입력과 결과를 사용해 측정합니다. 같은 데이터·규칙이면 결과가 재현되어야 합니다.
- **`k`:** 상위 몇 개 검색 결과만 평가할지를 정하는 절단 순위입니다. `@3`은 상위 세 결과만 본다는 뜻입니다.
- **Recall@k:** 정답 문서 중 상위 `k`에 검색된 비율입니다. 관련 문서를 놓치지 않는 정도를 봅니다.
- **Precision@k:** 상위 `k` 결과 중 정답 문서 비율입니다. 이 실습에서는 결과가 `k`개보다 적어도 분모를 `k`로 고정해 짧은 결과가 점수를 부풀리지 못하게 합니다.
- **Hit Rate@k:** 상위 `k`에 정답이 하나 이상 있던 질의의 비율입니다.
- **MRR:** 각 질의에서 첫 정답의 역순위를 평균낸 값입니다. 첫 정답이 1위면 1, 2위면 1/2입니다.
- **NDCG@k:** 정답이 앞 순위에 있을수록 더 높은 점수를 주는 지표입니다. 여러 정답 문서가 있을 때 순위 품질을 함께 봅니다.

하나의 지표만 목표로 삼으면 품질을 오해할 수 있습니다. Recall만 높이면 불필요한 문서를 많이 반환할 수 있고, 첫 정답만 보면 두 번째 정답 이후의 품질을 놓칠 수 있습니다. 따라서 이 장은 다섯 지표를 같은 고정 데이터에 함께 기록합니다.

## 4. 동작 구조

```text
고정 골든 데이터셋                 고정 Top-k 검색 결과
(질의, 정답 문서 ID)                 (case_id -> 문서 ID 순위)
          │                                      │
          └───────────────┬──────────────────────┘
                          ▼
               입력 계약 검증
     (사례 누락, 중복 ID, k 오류는 실패)
                          │
                          ▼
      Recall / Precision / Hit Rate / MRR / NDCG
                          │
                          ▼
              결정론적 평가 보고서
                          │
                          └──► 테스트·CI의 회귀 기준

LLM API · Vector DB · 네트워크 ─── 이 장의 기본 경로에서 사용하지 않음
```

`RetrievalCase`는 사례 ID, 질의, 정답 문서 ID를 가집니다. `evaluate_retrieval()`는 사례마다 기록된 문서 순위를 받아 평균 지표를 반환합니다. 시간 측정이나 랜덤 샘플링을 하지 않으므로, 코드와 입력이 같으면 결과도 같습니다.

## 5. 실습 환경

이 장에서 사용할 파일은 다음과 같습니다.

- `src/ai_platform/evaluation/datasets.py`: 공개 가능한 고정 질의, 정답 문서 ID, Top-3 순위를 정의합니다.
- `src/ai_platform/evaluation/retrieval_metrics.py`: 입력 계약과 다섯 검색 지표를 계산합니다.
- `examples/volume10/retrieval_quality.py`: 지표를 사람이 읽을 수 있는 형식으로 출력합니다.
- `tests/evaluation/test_retrieval_metrics.py`: 기준 점수와 오류 경계를 검증합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cd ~/projects/ai-platform-engineering-book
conda env update --file environment.yml --prune
```

`conda env update --file environment.yml --prune`는 프로젝트 가상환경과 pytest·ruff·mypy를 준비합니다. Windows Git Bash에서도 저장소 루트로 이동한 뒤 같은 Conda 환경 명령을 실행할 수 있습니다. 이 실습에는 환경 변수나 API 키가 필요하지 않습니다.

## 6. 단계별 실습

### 6.1 고정 데이터로 검색 지표 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
python examples/volume10/retrieval_quality.py
```

이 명령은 `FIXED_RETRIEVAL_CASES`와 `FIXED_RETRIEVAL_RESULTS_AT_3`만 사용합니다. 문서 임베딩, 검색 서버, LLM 호출을 수행하지 않습니다. 따라서 로컬과 CI에서 동일한 기준선을 확인하는 데 사용합니다.

### 6.2 지표와 입력 계약 테스트

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
pytest tests/evaluation/test_retrieval_metrics.py -q
```

테스트는 고정 데이터의 점수뿐 아니라 0 이하 `k`, 사례 누락, 중복 문서 ID를 거부하는지를 확인합니다. 실패를 조용히 무시하면 일부 질의만 측정한 평균이 보고될 수 있으므로 입력 계약도 품질 측정의 일부입니다.

### 6.3 수치 해석

이번 고정 결과에서 `benefits-enrollment`는 상위 3개에 정답 문서가 없습니다. 반면 `incident-response`는 두 정답 문서가 1위와 2위에 있습니다. 이 차이가 Recall, Hit Rate, MRR, NDCG에 어떻게 반영되는지 `tests/evaluation/test_retrieval_metrics.py`의 기대값과 함께 확인합니다.

다음 장에서는 이 작은 골든 데이터셋을 어떻게 대표성 있는 사례로 확장하고 버전 관리할지 다룹니다. 기준 데이터가 바뀌면 이전 점수와 직접 비교할 수 없으므로, 데이터 변경과 시스템 변경을 분리해 기록해야 합니다.

## 7. 코드 설명

`datasets.py`의 사례는 문서 본문 대신 문서 ID를 정답으로 사용합니다. 따라서 문서를 조회하지 않아도 "정답 문서가 상위 순위에 있는가"를 검증할 수 있습니다. 데이터와 결과가 소스에 고정되어 있어 API 비용이나 색인 상태가 측정값을 바꾸지 않습니다.

`evaluate_retrieval()`는 모든 골든 사례에 정확히 하나의 결과 묶음이 있는지 확인합니다. 또한 같은 문서 ID가 순위에 두 번 등장하면 실패시킵니다. 이런 중복은 하나의 정답을 여러 번 세거나 검색기 결함을 숨길 수 있습니다.

계산 시 각 사례의 점수를 먼저 구한 뒤 산술 평균을 냅니다. `Precision@k`의 분모를 항상 `k`로 사용하므로, 결과를 적게 반환하는 구현이 불리해집니다. NDCG는 1위 정답에 더 큰 가중치를 주고 가능한 이상 순위로 나누므로 0에서 1 사이의 값으로 해석합니다.

## 8. 정상 실행 결과

6.1 명령은 다음과 같은 출력을 포함해야 합니다.

```text
평가 사례: 4
Recall@3: 0.750000
Precision@3: 0.333333
Hit Rate@3: 0.750000
MRR: 0.625000
NDCG@3: 0.657732
```

6.2 명령은 설치된 pytest 버전에 따라 시간은 달라도 `passed`로 끝나야 합니다. 수치가 다르면 데이터셋이나 순위 결과가 바뀌었는지 먼저 확인합니다. 임의로 기대값만 갱신하거나 라이브 검색을 실행해 해결하지 않습니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `No module named ai_platform` | 저장소 루트 밖에서 시스템 Python을 실행했을 수 있습니다. | 저장소 루트에서 `conda env update --file environment.yml --prune` 후 `python ...`을 사용합니다. |
| `k must be a positive integer` | `k=0`, 음수, 불리언, 문자열을 전달했을 수 있습니다. | 상위 결과 수를 나타내는 양의 정수만 사용합니다. |
| `missing=` 또는 `unexpected=` 오류 | 골든 사례와 결과 사전의 `case_id`가 일치하지 않습니다. | 데이터셋과 결과에 같은 사례 ID가 정확히 한 번씩 있는지 확인합니다. |
| `must be unique` 오류 | 하나의 순위 목록에 같은 문서 ID가 반복됩니다. | Retriever 출력의 중복 제거 규칙을 확인하고 원본 순위를 수정합니다. |
| 지표가 예상과 다름 | 고정 데이터 또는 `k`가 변경되었을 수 있습니다. | 변경 목적을 기록하고 이전 데이터셋 버전과 같은 조건에서 비교합니다. |

## 10. 응용 실습

1. `RetrievalCase`를 하나 추가하고 정답 문서가 2개인 경우를 만듭니다. 두 문서가 1·2위일 때와 2·3위일 때 NDCG@3가 왜 달라지는지 테스트로 증명합니다.
2. 동일한 골든 사례에 서로 다른 Retriever 두 개의 기록된 순위를 준비합니다. 두 결과를 같은 `k`로 평가하고 Recall만으로 우열을 결정하면 안 되는 사례를 찾습니다.
3. 빈 답변이 올바른 no-answer 질의를 지원하려면 현재 계약을 어떻게 확장해야 하는지 설계합니다. 관련 문서가 없는 사례의 Recall 정의, 기대 행동, 별도 지표를 문서로 먼저 정합니다.

## 11. 실무 적용

운영 평가에서는 골든 데이터셋을 기능 코드와 별도로 버전 관리하고, 각 사례의 출처·라벨 근거·검토자·변경 이유를 기록합니다. 새로운 정책이나 문서가 추가되면 대표 사례를 추가하되, 과거 결과와 비교할 때는 데이터셋 버전과 `k`를 함께 보고합니다.

오프라인 검색 지표는 필요조건이지 충분조건이 아닙니다. 답변 정확도, 인용 정확성, 환각률, Router 정확도, Agent Task Success, p95 지연 시간, 토큰·비용을 목적에 맞게 결합해야 합니다. LLM-as-a-Judge와 사람 평가는 판정 프롬프트, 샘플링, 익명화, 검토 합의도 함께 관리합니다.

> [!TIP]
> 릴리스 비교표에는 최소한 코드 버전, 데이터셋 버전, `k`, 사례 수, 각 지표, 실패 사례 ID를 함께 기록합니다. 평균 점수 하나만 남기면 왜 좋아지거나 나빠졌는지 추적하기 어렵습니다.

## 12. 과제

- **기본:** Recall@3, Precision@3, Hit Rate@3가 각각 어떤 질문에 답하는지 한 문장씩 작성합니다.
- **응용:** 상위 3개 중 정답이 3위에 한 번만 나타나는 사례의 MRR과 NDCG@3를 손으로 계산한 뒤 테스트 기대값으로 확인합니다.
- **심화:** 실제 운영 로그를 골든 데이터셋 후보로 수집할 때 개인정보, 라벨 품질, 대표성, 데이터 드리프트 관점의 승인 절차를 설계합니다. 실제 로그나 외부 API는 사용하지 않습니다.

## 14. 핵심 정리

좋은 평가의 출발점은 고정된 기준과 재현 가능한 계산입니다. 이번 장은 공개 가능한 골든 사례와 기록된 순위를 사용해 검색 품질을 수치화했습니다. 다섯 지표는 서로 다른 실패를 드러내며, 입력 계약은 부분 평가나 중복 결과로 인한 왜곡을 막습니다. 다음 단계는 골든 데이터셋을 신중하게 확장하고, 검색 외에 답변·라우팅·Agent·운영 지표까지 같은 원칙으로 연결하는 일입니다.
