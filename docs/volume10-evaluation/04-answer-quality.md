# 응답 정확도·환각·인용 평가

## 1. 학습 목표

이 장을 완료하면 다음을 할 수 있어야 합니다.

- 검색 품질과 최종 답변 품질을 별도의 계약으로 측정해야 하는 이유를 설명한다.
- 답변 가능(`answer`)과 답변 보류(`abstain`) 기대 동작을 사실 주장과 분리한다.
- 고정된 사실 ID와 허용 인용 문서 ID로 답변 정확도, 보류 정확도, 환각률, 인용 정확도를 결정론적으로 계산한다.
- 하나의 평균 점수 대신 사례별 지원되지 않은 주장과 인용을 찾아낸다.
- `office-parking` no-answer 사례의 보류 실패를 재현하고 해석한다.
- LLM-as-a-Judge와 사람 평가가 필요한 의미·완전성 문제를 이 고정 라벨 평가의 한계와 함께 설명한다.

## 2. 왜 필요한가

Retriever가 관련 문서를 가져와도 최종 답변은 문서를 잘못 해석하거나, 문서에 없는 내용을 추가하거나, 관련 없는 문서를 인용할 수 있습니다. 반대로 좋은 문장을 생성했더라도 근거가 없는 no-answer 질의에 답변하면 사용자를 오도할 수 있습니다. 검색 Recall만으로는 이 실패를 알 수 없습니다.

이 장은 자연어 문장 전체를 모델로 채점하지 않습니다. 대신 사람이 검토한 고정 사실 ID와 허용 인용 문서 ID를 기준으로, 기록된 답변의 행동·주장·인용을 비교합니다. 따라서 동일한 입력에서는 항상 같은 수치와 같은 실패 사례가 나옵니다. 이는 Prompt, Retriever, 모델을 바꾸기 전후의 회귀 기준선입니다.

> [!WARNING]
> 고정 사실 ID는 교육용 라벨이지 실제 정책 본문이 아닙니다. 고객 질의, 개인정보, 비공개 문서, API 키를 넣거나 라이브 LLM·Judge API를 호출하지 않습니다. 실제 답변을 평가할 때는 승인된 비식별화, 라벨 검토, 접근 권한, 보존 기간을 별도로 관리해야 합니다.

## 3. 핵심 개념

- **답변 정확도(Answer Accuracy):** 기대 동작과 일치하고, `answer` 사례에서 모든 필수 사실을 주장하며, 지원되지 않은 사실을 주장하지 않은 사례 비율입니다. 이 지표는 인용 정확도와 분리합니다.
- **보류 정확도(Abstention Accuracy):** `abstain` 사례에서 실제로 보류한 비율입니다. no-answer를 0 Recall로 섞지 않고 별도로 봅니다.
- **환각률(Hallucination Rate):** 기록된 모든 사실 주장 중 고정 라벨의 지원 사실에 없는 주장 비율입니다. 주장 수를 분모로 쓰므로 응답 길이나 사례 수와 혼동하지 않습니다.
- **인용 정확도(Citation Accuracy):** 기록된 모든 인용 문서 중 해당 사례에서 허용된 문서 비율입니다. 인용이 하나도 없으면 이 구현은 0으로 반환합니다.
- **지원 사실 ID:** 사람이 검토해 해당 사례에 허용한 최소 사실의 안정된 식별자입니다. 자연어 유사도 점수가 아닙니다.
- **허용 인용 문서 ID:** 해당 사례의 주장을 뒷받침할 수 있는 고정 문서 식별자입니다. 인용 정확도는 인용의 내용 적합성을 완전히 증명하지는 않습니다.
- **기록 답변(Recorded Answer):** 라이브 호출 결과 대신 고정한 `response_mode`, `asserted_fact_ids`, `cited_document_ids`입니다.

이 장의 답변 정확도는 의도적으로 인용 정확도와 별개입니다. 예를 들어 `benefits-enrollment`는 필요한 사실을 주장했으므로 답변 정확도에는 성공하지만, `identity-access`를 인용했으므로 인용 정확도에는 실패합니다. 하나의 점수로 합치면 무엇을 고쳐야 하는지가 사라집니다.

## 4. 동작 구조

```text
고정 GoldenDataset                  고정 AnswerCase / RecordedAnswer
(answer · abstain · 관련 문서)       (행동 · 사실 ID · 인용 문서 ID)
             │                                    │
             └────────────────┬───────────────────┘
                              ▼
                   입력 계약 검증
       (완전한 case_id · 중복 없는 ID · 보류의 빈 주장/인용)
                              ▼
                   사례별 AnswerCaseMetrics
     (행동 일치 · 사실 지원 · 지원/미지원 인용 · 환각 주장)
                              ▼
    Answer Accuracy · Abstention Accuracy · Hallucination Rate · Citation Accuracy
                              ▼
              고정 데이터셋 버전과 함께 회귀 리포트

LLM API · LLM-as-a-Judge · Vector DB · 네트워크 · 시계 · 난수 ── 사용하지 않음
```

`evaluate_answer_cases()`는 입력 사례 순서대로 사례별 결과를 반환합니다. `evaluate_answers()`는 바로 그 결과를 집계하므로 사례 보고서와 전체 수치가 다른 계산 경로를 사용하지 않습니다. 모든 사례의 결과가 있어야 하며, 일부 성공 사례만 제출해 평균을 높이는 입력은 실패합니다.

## 5. 실습 환경

이 장에서 사용할 산출물은 다음과 같습니다.

- `src/ai_platform/evaluation/answer_metrics.py`: 답변·보류·사실·인용 입력 계약과 결정론적 지표를 정의합니다.
- `src/ai_platform/evaluation/datasets.py`: 기존 골든 사례에서 파생한 고정 답변 라벨과 의도적인 실패 답변을 정의합니다.
- `examples/volume10/answer_quality.py`: 전체 답변 기준선을 출력합니다.
- `tests/evaluation/test_answer_metrics.py`: 기준 수치, 사례별 실패, 누락 결과, 모순된 라벨을 검사합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv sync --all-groups
```

이 실습에는 환경 변수, API 키, 모델 서버, 벡터 데이터베이스가 필요하지 않습니다. Windows Git Bash에서도 저장소 루트에서 같은 `uv` 명령을 실행할 수 있습니다.

## 6. 단계별 실습

### 6.1 고정 답변 품질 기준선 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run python examples/volume10/answer_quality.py
```

명령은 다섯 고정 사례를 평가합니다. 네 개 `answer` 사례는 필수 사실을 모두 주장합니다. `office-parking`은 관련 문서가 없는 `abstain` 사례인데도 답변과 사실·인용을 기록했으므로 보류 실패 및 환각으로 드러납니다.

### 6.2 답변·환각·인용 계약 테스트

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/evaluation/test_answer_metrics.py -q
```

테스트는 기준 수치뿐 아니라 no-answer 위반, 부정확한 인용, 누락 사례, 사전 키와 기록 답변 `case_id`의 불일치를 검사합니다. `abstain` 응답에 주장이나 인용을 넣는 입력도 조용히 계산하지 않고 거부합니다.

### 6.3 사례별 실패를 확인하는 방법

`evaluate_answer_cases()`의 `unsupported_fact_ids`와 `unsupported_citation_ids`를 확인합니다. 고정 기준선에서 `benefits-enrollment`는 `identity-access`라는 부정확한 인용 하나를 보이고, `office-parking`은 `parking-pass-application-is-available`이라는 지원되지 않은 사실과 `service-overview` 인용을 보입니다. 평균값만 보는 대신 이 ID를 리포트에 남겨 원인을 분리합니다.

### 6.4 수치 비교 조건 고정

Prompt 또는 모델 후보를 비교할 때는 같은 `volume10-support-policy@1.0.0`, 같은 사실 ID 정의, 같은 인용 허용 목록, 같은 사례 집합을 사용합니다. 라벨을 수정하거나 사례를 추가하면 데이터셋 버전과 변경 이유를 먼저 기록합니다. 다른 기준에서 나온 0.8과 0.8을 같은 품질이라고 해석하지 않습니다.

## 7. 코드 설명

`AnswerCase`는 각 사례의 기대 동작, 지원 사실, 허용 인용을 고정합니다. `answer` 사례에는 최소 하나의 사실과 인용이 있어야 합니다. `abstain` 사례에는 둘 다 없어야 합니다. 이 구분으로 관련 문서가 없는 질의에 대한 보류를 검색 실패와 구별합니다.

`RecordedAnswer`는 자연어 문장 대신 검토 가능한 ID 목록을 받습니다. 보류 응답은 주장과 인용을 가질 수 없습니다. `evaluate_answer_cases()`는 각 주장과 인용을 고정 허용 집합과 비교해 지원되지 않은 ID를 순서대로 보관합니다. 응답 행동이 기대와 같고, 지원되지 않은 주장이 없고, answer 사례의 모든 필수 사실이 있으면 `answer_is_correct`입니다.

`evaluate_answers()`는 사례별 결과를 집계합니다. 환각률의 분모는 주장 수 6이며 지원되지 않은 주장은 `office-parking`의 하나뿐입니다. 인용 정확도의 분모는 인용 수 6이며 네 개는 허용 문서입니다. 인용 누락의 문제는 이 지표 단독으로 잡히지 않으므로, 운영 기준에는 후속 장의 인용 완전성 또는 사례별 필수 인용 규칙을 추가해야 합니다.

## 8. 정상 실행 결과

6.1 명령은 다음 출력을 포함해야 합니다.

```text
Evaluation cases: 5
Answer accuracy: 0.800000
Abstention accuracy: 0.000000
Hallucination rate: 0.166667
Citation accuracy: 0.666667
```

`Answer accuracy`가 0.8인 이유는 `office-parking`만 기대한 보류를 따르지 않았기 때문입니다. `Abstention accuracy`가 0인 이유도 같은 사례입니다. `Hallucination rate`는 여섯 주장 중 지원되지 않은 주장이 하나여서 약 0.166667입니다. `Citation accuracy`는 여섯 인용 중 허용 문서가 네 개여서 약 0.666667입니다.

6.2 명령은 pytest 실행 시간과 무관하게 `passed`로 끝나야 합니다. 수치가 다르면 라이브 모델을 호출하거나 기대값만 바꾸지 말고, 데이터셋 버전·사실 ID·기록 답변·인용 허용 목록이 기준선과 같은지 확인합니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `recorded answers must match case ids` | 일부 사례 결과가 빠졌거나 예상 밖 ID가 있다. | 모든 `AnswerCase`에 정확히 하나의 `RecordedAnswer`를 제공한다. |
| `key and case_id must match` | 결과 사전의 키와 답변 내부 ID가 다르다. | 같은 안정된 `case_id`를 키와 객체에 사용한다. |
| `abstain responses must not assert facts` | 보류 응답에 사실 주장이 기록되었다. | 보류 행동과 답변 주장을 분리하고 빈 사실 목록을 사용한다. |
| `abstain responses must not cite documents` | 보류 응답에 근거처럼 보이는 문서가 남았다. | no-answer 정책을 재검토하고 보류 기록의 인용을 비운다. |
| 환각률은 낮지만 보류 정확도가 낮다 | 지원되지 않은 주장이 적어도 no-answer에 답했을 수 있다. | `abstain` 사례의 행동 일치와 사실 ID를 함께 점검한다. |
| 인용 정확도가 낮다 | 허용되지 않은 문서 ID를 인용했다. | 인용 추출 규칙과 사례의 허용 인용 라벨을 검토한다. |
| 인용이 없는데 인용 정확도가 0이다 | 이 구현은 분모가 0이면 0을 반환한다. | 누락 인용을 별도 실패로 기록하고 후속 완전성 지표를 추가한다. |

## 10. 응용 실습

1. 고정 `answer` 사례 하나에 필수 사실을 두 개 이상 정의하고, 하나가 빠진 답변이 왜 답변 정확도 실패인지 테스트로 증명합니다.
2. no-answer 사례에 올바른 `abstain` 기록을 만들어 보류 정확도와 환각률이 어떻게 변하는지 계산합니다. 외부 모델은 호출하지 않습니다.
3. 인용 정확도는 같지만 인용 누락 수가 다른 두 기록 답변을 설계하고, 왜 인용 완전성 지표가 추가로 필요한지 설명합니다.
4. 사람 검토자가 자연어 주장을 사실 ID에 매핑하는 라벨 지침을 작성합니다. 불일치 해결, 라벨 버전, 검토 근거를 포함합니다.

## 11. 실무 적용

운영 환경에서는 답변 문장을 원자적 주장 단위로 분해하고, 각 주장에 근거 스냅샷·문서 구간·검토자·라벨 지침 버전을 연결합니다. 인용 평가는 문서 ID 일치뿐 아니라 인용 구간이 실제 주장을 지지하는지, 필수 주장이 모두 인용되었는지, 오래된 문서를 인용하지 않았는지도 확인해야 합니다.

LLM-as-a-Judge는 넓은 자연어 범위를 빠르게 훑을 수 있지만 프롬프트와 Judge 모델 변경에 따라 판정이 변할 수 있습니다. 사람 평가는 고위험 사례와 라벨 감사에 필요하지만 비용과 합의 규칙이 필요합니다. 따라서 고정 규칙 평가는 빠른 회귀 차단에, Judge와 사람 평가는 의미·완전성·안전성의 보완 평가에 사용합니다. 어떤 방식이든 익명화된 승인 데이터만 사용합니다.

> [!TIP]
> 릴리스 리포트에는 코드 커밋, 데이터셋 ID·버전, 라벨 지침 버전, 사례 수, 답변·보류·환각·인용 지표, 지원되지 않은 사실 ID, 부정확한 인용 ID를 함께 기록하세요. 평균이 같아도 실패 사례가 바뀌면 같은 위험이 아닙니다.

## 12. 과제

- **기본:** 답변 정확도와 인용 정확도를 하나의 점수로 합치지 않는 이유를 한 문단으로 설명합니다.
- **응용:** `office-parking`을 올바르게 보류하도록 고정 기록을 바꿨다고 가정하고, 보류 정확도와 환각률의 새 분자·분모를 계산합니다.
- **심화:** 실제 정책 답변을 사람과 LLM-as-a-Judge가 함께 평가하는 절차를 설계합니다. 주장 분해, 판정 불일치, 개인정보 비식별화, 라벨 버전, 샘플링, 승인 기준을 포함하며 실제 API는 호출하지 않습니다.

- [ ] `answer`와 `abstain`의 사실·인용 계약을 구분할 수 있다.

## 14. 핵심 정리

최종 답변 평가는 검색 성공 여부만으로 끝나지 않습니다. 기대 행동, 지원 사실, 인용 문서를 고정 라벨로 분리하면 보류 실패, 환각 주장, 부정확한 인용을 같은 입력에서 재현할 수 있습니다. 이 장의 결정론적 ID 비교는 빠르고 감사 가능하지만 자연어의 의미, 인용 구간, 누락된 정보의 완전성을 모두 판정하지는 않습니다. 그러므로 회귀 기준선 위에 사람 평가와 LLM-as-a-Judge를 신중하게 추가하고, 다음 장에서 Router와 Agent의 작업 성공까지 평가 범위를 확장합니다.
