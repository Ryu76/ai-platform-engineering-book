# 핵심 정리: 안전한 LLM 호출에서 오프라인 CLI 경계까지

## 1. 학습 목표

이 장을 마치면 Volume 01에서 만든 AI 업무 처리 플랫폼의 첫 사용자 입구를 한 흐름으로 설명할 수 있습니다. 환경 변수 기반 설정, 메시지 구조, 생성 파라미터, 스트리밍, 제한된 재시도, 토큰 사용량, CLI 대화 이력이 각각 어떤 안전 경계를 만드는지 정리하고, 실제 API 키·네트워크 없이 회귀 검사를 실행할 수 있습니다.

## 2. 왜 필요한가

LLM 애플리케이션은 모델의 답변만 연결해서 끝나지 않습니다. 입력을 어디로 보내는지, 실패를 어떻게 보이는지, 이전 대화를 얼마나 보관하는지, 비용을 어떻게 추정하는지가 함께 설계되어야 합니다. 이 기반이 없으면 다음 Volume에서 Prompt 템플릿을 추가할 때도 사용자 입력과 시스템 지시문이 섞이거나 테스트가 외부 계정에 의존할 수 있습니다.

Volume 01은 이후 RAG, Tool, Router, Agent가 연결될 공통 입구를 다음 원칙으로 고정합니다.

- 비밀값은 코드가 아니라 환경 변수에서 읽고 오류·로그에 다시 쓰지 않습니다.
- 모델 요청은 역할이 있는 메시지 목록과 명시적인 시간 제한을 사용합니다.
- 생성 파라미터와 사용량·비용 추정은 관찰 가능한 값으로 다룹니다.
- 실패·빈 응답은 성공 대화 이력으로 저장하지 않습니다.
- `--offline-demo`, Mock, 별도 프로세스 통합 테스트로 외부 전송 없이 실행 경계를 검사합니다.

> [!WARNING]
> `--offline-demo`가 없는 라이브 CLI는 설정된 제공자에 사용자 입력을 전송하고 비용을 만들 수 있습니다. Volume 01의 학습 검증에는 실제 API 키, 회사 문서, 개인정보를 사용하지 말고 오프라인 경로와 Mock 테스트만 사용합니다.

## 3. 핵심 개념

**토큰(Token)** 은 모델이 텍스트를 처리하는 단위입니다. 입력 토큰과 출력 토큰의 합은 컨텍스트 윈도우와 비용에 영향을 줍니다. `max_output_tokens`는 출력의 상한이며, 대화 이력 한도는 다음 요청으로 전달하는 과거 턴 수의 상한입니다. 둘 중 하나만 제한해서는 장문 요청의 비용과 길이를 충분히 통제할 수 없습니다.

**메시지(Message)** 는 `system`, `user`, `assistant` 역할과 내용을 함께 가진 요청 단위입니다. 시스템 메시지는 플랫폼의 동작 원칙을 지정하고, 사용자 입력은 신뢰되지 않은 데이터입니다. 사용자 입력이 시스템 지시문을 바꾸거나 권한을 얻을 수 없도록 역할을 분리하는 관점은 다음 Volume의 Prompt Injection 방어로 이어집니다.

**생성 파라미터(Generation Parameters)** 중 `temperature`와 `top_p`는 후보 선택의 다양성에 관여합니다. 둘을 동시에 크게 바꾸기보다 한 번에 하나를 바꾸고, 목적·입력·버전이 같은 테스트에서 비교해야 원인을 해석할 수 있습니다. Stop sequence와 최대 출력 토큰은 출력 형식과 비용을 제한하는 보조 경계입니다.

**스트리밍(Streaming)** 은 완성된 답변을 한 번에 기다리지 않고 조각 단위로 표시하는 방식입니다. 사용자 체감 대기 시간은 줄일 수 있지만, 중간 조각은 최종 답변이 아니므로 성공 사용량·완료 상태와 분리해 다룹니다.

**제한된 재시도(Bounded Retry)** 는 일시적인 시간 초과나 연결 실패를 정해진 횟수 안에서 다시 시도하는 정책입니다. 인증 오류나 잘못된 입력처럼 재시도로 해결되지 않는 오류에는 적용하지 않습니다. 무한 재시도는 비용과 대기 시간을 키우므로 안전한 기본값이 아닙니다.

**오프라인 검증 경계(Offline Verification Boundary)** 는 실제 제공자 대신 `OfflineDemoClient`와 `ScriptedClient`를 사용해 CLI의 시작·입력·응답·종료 및 오류 분기를 재현하는 방법입니다. 이는 모델 답변 품질을 평가하지 않지만, 외부 계정·네트워크 없이 프로그램 계약의 회귀를 발견합니다.

## 4. 동작 구조

```text
사용자 입력
   │
   ├── /exit, /quit, 빈 입력 ─────────► 로컬 처리, 제공자 전송 없음
   │
   ▼
ConversationHistory.messages_for()
   │  system + 성공한 최근 사용자/assistant 턴 + 새 user 메시지
   ▼
LlmClient.complete() 또는 stream()
   │
   ├── 시간 초과·연결·응답 오류 ──────► 안전한 안내, 이력 미변경
   │
   ▼
성공 응답 + Token Usage
   │
   ├── usage.py ─────────────────────► 가격표 기반 비용 추정
   └── ConversationHistory.record_success()
                                      │
                                      ▼
                             다음 Volume의 Prompt 입구

테스트 경계
  Mock 단위 테스트 ───────────────────► ScriptedClient, 외부 전송 없음
  오프라인 통합 테스트 ───────────────► chat_cli.py --offline-demo
```

## 5. 실습 환경

Volume 01의 결과물은 같은 저장소의 다음 경로에 있습니다.

- `src/ai_platform/core/settings.py`: 환경 변수와 시간 제한을 검증합니다.
- `src/ai_platform/llm/client.py`: 완료 요청, 스트리밍, 오류 유형을 분리합니다.
- `src/ai_platform/llm/usage.py`: 제공자 청구서가 아닌 명시적 가격표 기반 비용 추정을 수행합니다.
- `src/ai_platform/llm/chat.py`: 성공한 대화 턴만 제한적으로 보관하는 CLI 루프를 제공합니다.
- `examples/volume01/chat_cli.py`: 라이브 모드와 `--offline-demo`를 구분합니다.
- `tests/unit/`: 설정, 클라이언트, 사용량, 대화 이력을 Mock으로 검사합니다.
- `tests/integration/test_volume01_chat_cli.py`: 오프라인 CLI를 별도 Python 프로세스로 검사합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cd ~/projects/ai-platform-engineering-book
uv sync --all-groups
```

첫 명령은 WSL 안의 저장소로 이동합니다. 두 번째 명령은 프로젝트와 검사 도구를 준비합니다. Windows에서 WSL을 쓴다면 Windows PowerShell 경로와 WSL 경로를 섞지 않습니다.

## 6. 단계별 실습

### 6.1 안전한 오프라인 사용자 흐름 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
printf 'Context Window는 무엇인가요?\n/exit\n' | uv run python examples/volume01/chat_cli.py --offline-demo
```

이 명령은 질문과 종료 명령을 표준 입력으로 전달합니다. `--offline-demo`는 설정과 네트워크를 읽지 않으므로 API 키 없이 실행됩니다. 출력에 시작 안내, `오프라인 데모 응답`, `대화를 마칩니다.`가 차례로 포함되는지 확인합니다.

### 6.2 핵심 단위·통합 테스트 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/unit/test_llm_client.py tests/unit/test_chat.py tests/unit/test_usage.py -q
uv run pytest tests/integration/test_volume01_chat_cli.py -q
```

첫 명령은 클라이언트의 성공·실패·스트리밍, 대화 이력과 안전한 종료, 토큰 사용량·비용 추정을 확인합니다. 두 번째 명령은 실제 Python 하위 프로세스에서 오프라인 CLI가 시작하고 종료되는지 확인합니다. 두 명령 모두 실제 LLM 제공자에 요청하지 않습니다.

### 6.3 전체 품질 검사 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
bash scripts/run_all_tests.sh
```

이 명령은 `ruff check .`, `mypy src`, 문서·링크·코드 블록·비밀값 검사, 전체 `pytest`를 순서대로 실행합니다. 정상 종료는 Volume 01의 코드와 문서 계약이 현재 저장소에서 함께 통과했다는 뜻입니다. 실패하면 다음 Volume을 시작하기 전에 실패한 검사와 해당 파일을 먼저 수정합니다.

## 7. 코드 설명

`LlmSettings.from_environment()`는 모델명, API 키, 기본 URL, 시간 제한을 한 곳에서 읽고 검증합니다. 클라이언트 코드는 이 설정을 주입받으므로 테스트가 실제 환경 변수를 요구하지 않습니다.

`LlmClient`는 제공자 응답을 `LlmResponse`로 바꾸고, 호출자가 처리할 수 있는 시간 초과·연결·인증·응답 형식 오류를 구분합니다. 사용자에게 보여 주는 CLI는 원본 예외나 요청 헤더를 출력하지 않아 비밀값 노출 범위를 줄입니다.

`ConversationHistory`는 새 질문을 요청용 메시지에만 먼저 추가합니다. `complete()`가 성공하고 내용이 비어 있지 않을 때만 `record_success()`로 사용자·Assistant 쌍을 저장합니다. 실패한 요청을 이력에 넣지 않으므로 다음 요청이 실패 내용을 사실처럼 받지 않습니다.

`OfflineDemoClient`와 `ScriptedClient`는 공통 `complete(messages)` 계약을 구현합니다. 전자는 CLI 전체 실행을, 후자는 특정 성공·실패 순서를 주입하는 단위 테스트를 지원합니다. 이 의존성 주입 구조는 Volume 02에서 Prompt Runner를 붙여도 테스트 경계를 보존하는 기반입니다.

## 8. 정상 실행 결과

6.1 명령의 출력은 다음과 유사합니다. 파이프 입력에서는 프롬프트와 응답이 같은 줄에 보일 수 있습니다.

```text
AI 업무 처리 플랫폼 챗봇입니다. 종료하려면 /exit 또는 /quit을 입력하세요.
사용자> AI> 오프라인 데모 응답: 'Context Window는 무엇인가요?' 요청을 기록했습니다.
사용자> 대화를 마칩니다.
```

6.2와 6.3의 정상 결과에는 각각 `passed`, `All checks passed!`, `Success: no issues found`와 같은 성공 표시가 포함됩니다. 테스트 개수는 이후 장의 회귀 테스트가 추가되면 바뀔 수 있으므로, 고정된 개수보다 종료 코드 0과 실패 없음으로 판단합니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `No module named ai_platform` | 저장소 밖의 Python을 실행했거나 동기화가 되지 않았습니다. | 저장소 루트에서 `uv sync --all-groups` 후 `uv run ...` 명령을 사용합니다. |
| 제공자 설정 오류가 표시됨 | `--offline-demo` 없이 라이브 모드를 실행했습니다. | 검증 명령에 `--offline-demo`가 있는지 확인합니다. 학습 검증을 위해 `.env`나 키를 만들 필요가 없습니다. |
| 테스트가 시간 초과됨 | 종료 명령이 입력되지 않았거나 CLI 종료 분기가 변경됐을 수 있습니다. | 입력에 `/exit\n`이 있는지와 `run_chat_loop()`의 종료 처리를 확인합니다. |
| 비용 추정이 청구 금액과 다름 | 가격표·통화·입출력 토큰 기준이 제공자 청구 기준과 다를 수 있습니다. | `usage.py`의 가격표와 모델명을 명시하고 추정값을 청구서로 사용하지 않습니다. |
| 출력에 예외 또는 민감한 문자열이 보임 | 안전한 오류 변환을 우회해 원본 예외를 출력했을 수 있습니다. | 오류 안내를 고정된 사용자용 문구로 복원하고 관련 단위 테스트를 실행합니다. |

## 10. 응용 실습

1. `ConversationHistory(max_turns=2)`로 세 번 성공한 대화를 기록하고, 다음 요청에서 가장 오래된 완성 턴이 빠지는지 `ScriptedClient` Mock 테스트로 확인합니다.
2. 같은 입력과 메시지 구조에서 `temperature`만 바꾼 Prompt 비교 표를 작성합니다. 라이브 모델 응답을 저장하지 말고 오프라인 데이터나 승인된 샘플을 사용합니다.
3. `/help`를 로컬 명령으로 설계합니다. 도움말이 `complete()`를 호출하지 않고, 라이브 모드의 외부 전송 경고를 보여 주는지 단위 테스트를 작성합니다.

## 11. 실무 적용

운영 환경에서는 모델명, 최대 출력 토큰, 시간 제한, 재시도 횟수, 사용자별 이력 한도, 비용 상한을 정책으로 관리합니다. 관측 로그에는 요청 ID, 모델명, 지연 시간, 성공 여부, 토큰 수처럼 필요한 최소 정보만 기록하고 API 키·Authorization 헤더·전체 프롬프트·개인정보는 기록하지 않습니다.

CLI의 메모리 이력은 프로세스가 끝나면 사라지고 여러 인스턴스에서 공유되지 않습니다. 영속화가 필요해지는 시점에는 암호화, 사용자별 접근 제어, 보존 기간, 삭제 요청 처리, 감사 로그를 먼저 설계합니다. 다음 Volume의 Prompt 템플릿은 이 사용자 입구를 확장하지만, 외부 문서나 사용자 입력을 시스템 지시문으로 취급하지 않는 역할 분리를 유지해야 합니다.

## 12. 과제

- **기본:** `--offline-demo`와 라이브 모드의 데이터 전송·비용·재현성 차이를 설명합니다.
- **응용:** 시간 초과, 인증 오류, 잘못된 응답 형식 각각에 재시도가 적절한지 판단하고 근거를 작성합니다.
- **심화:** Prompt 템플릿을 추가한다는 가정 아래, 시스템 지시문·사용자 입력·외부 문서·모델 출력을 분리한 메시지 설계와 Mock 테스트 계획을 작성합니다.

## 14. 핵심 정리

Volume 01은 AI 업무 처리 플랫폼의 가장 작은 LLM 사용자 경계를 만들었습니다. 설정 검증과 역할 기반 메시지는 요청의 형태를 고정하고, 생성 파라미터·스트리밍·사용량은 품질과 비용을 관찰하게 합니다. 오류 처리와 제한된 재시도는 실패를 통제하며, 제한된 성공 이력은 문맥과 비용을 함께 관리합니다. 마지막으로 오프라인 CLI, Mock, 통합 테스트는 실제 키·네트워크 없이 이 경계가 계속 안전하게 동작하는지 검증합니다. Volume 02에서는 이 검증된 입구에 버전 관리 가능한 Prompt 템플릿, 구조화된 출력, 입력 검증과 Prompt Injection 방어를 연결합니다.
