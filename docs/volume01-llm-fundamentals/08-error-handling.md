# 오류 처리와 제한된 재시도

## 1. 학습 목표

이 장을 마치면 LLM 호출 실패를 설정 오류, 시간 초과, 네트워크 오류, 제공자 HTTP 오류, 응답 형식 오류로 구분할 수 있습니다. 또한 재시도 가능한 일시 오류만 제한된 횟수와 지수 백오프로 다시 시도하고, API 키·사용자 원문을 오류 메시지나 로그에 남기지 않는 호출 경계를 구현할 수 있습니다.

## 2. 왜 필요한가

LLM 호출 실패를 모두 같은 방식으로 다시 보내면 문제가 커집니다. 잘못된 API 키(401)를 재시도해도 성공하지 않으며, 입력 형식 오류(400)를 반복하면 비용과 제공자 부하만 늘어납니다. 반대로 일시적인 503, 429, 연결 단절, 시간 초과는 짧은 대기 뒤 성공할 수 있습니다.

AI 업무 처리 플랫폼은 이후 Router, RAG, Agent가 모두 같은 LLM 경계를 사용할 수 있도록 실패 원인을 분류해야 합니다. 호출자에게는 안전한 안내를 주고, 운영 로그에는 비밀값 없이 오류 종류·상태 코드·시도 횟수만 남기는 것이 출발점입니다.

## 3. 핵심 개념

**시간 초과(timeout)** 는 정해 둔 시간 안에 제공자가 응답하지 않은 상태입니다. `LLM_TIMEOUT_SECONDS`는 한 번의 HTTP 요청에 적용됩니다. 시간 초과는 일시적일 수 있지만, 무한 대기는 서비스의 작업자와 사용자 경험을 모두 악화시킵니다.

**재시도(retry)** 는 실패한 요청을 다시 보내는 일입니다. 이 프로젝트의 `RetryPolicy`는 `max_attempts`를 1~5로 제한하고, 첫 실패 뒤 `base_delay_seconds`, 다음 실패 뒤 두 배의 시간을 기다리는 지수 백오프(exponential backoff)를 사용합니다. `max_attempts=3`, 기본 대기 0.5초라면 최대 세 번 시도하고 대기는 0.5초, 1.0초입니다.

다음 표는 현재 `LlmClient.complete()`의 정책입니다.

| 오류 | 예 | 자동 재시도 |
|---|---|---|
| 설정 오류 | 키·모델 누락, 잘못된 파라미터 | 아니오 |
| 응답 형식 오류 | `choices`가 없는 성공 응답 | 아니오 |
| 인증·입력 HTTP 오류 | 400, 401, 403, 404 | 아니오 |
| 일시 HTTP 오류 | 429, 500, 502, 503, 504 | 명시적 `RetryPolicy`가 있을 때만 |
| 네트워크·시간 초과 | 연결 실패, 요청 시간 초과 | 명시적 `RetryPolicy`가 있을 때만 |

> [!WARNING]
> 재시도는 같은 요청을 다시 실행합니다. 결제, 파일 쓰기, 메일 발송처럼 중복 실행이 위험한 작업에는 멱등성(idempotency) 키 또는 사람 승인이 필요합니다. 이 Volume의 텍스트 완료 요청은 재시도를 선택할 수 있지만, 이미 일부 텍스트를 보낸 스트림은 자동 재시도하지 않습니다.

## 4. 동작 구조

```text
ChatMessage
    │
    ▼
LlmClient.complete(..., RetryPolicy?)
    │
    ├── 성공(2xx) ──────────────► LlmResponse
    │
    └── 실패
         ├── 설정/응답 형식/400·401·403·404 ─► 즉시 예외 반환
         └── 네트워크/시간 초과/429·5xx
                 │
                 ├── 남은 시도 있음 ─► 0.5s, 1.0s ... 대기 후 재요청
                 └── 한도 도달 ──────► 안전한 예외 반환

Mock ScriptedTransport ─► 외부 네트워크 없이 위 분기를 검증
```

## 6. 단계별 실습

### 6.1 외부 호출 없이 오류 계약 검증

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/unit/test_llm_client.py -q
```

정상 결과에는 `503 → 성공`의 한 번 재시도, 401의 즉시 실패, 최대 3회 시도와 `0.1`, `0.2`초 백오프를 검증한 테스트가 포함됩니다. 테스트의 대기 함수는 리스트 기록용 Mock이므로 실제로 기다리거나 외부 전송하지 않습니다.

### 6.2 제한된 정책으로 완료 요청 호출

`examples/volume01/error_handling.py`의 핵심은 다음과 같습니다.

```python
client = LlmClient(
    model=settings.model,
    api_key=settings.api_key,
    base_url=settings.base_url,
    timeout_seconds=settings.timeout_seconds,
    retry_policy=RetryPolicy(max_attempts=3, base_delay_seconds=0.5),
)

try:
    response = client.complete([ChatMessage(role="user", content="플랫폼 상태를 한 문장으로 설명하세요.")])
except LlmTimeoutError:
    print("요청 시간이 초과되었습니다. 잠시 뒤 다시 시도하세요.")
except LlmNetworkError:
    print("제공자 연결에 실패했습니다. 네트워크와 제공자 상태를 확인하세요.")
except LlmRemoteError as error:
    print(f"제공자가 요청을 거부했습니다. 상태 코드: {error.status_code}")
else:
    print(response.content)
```

`RetryPolicy`를 생략하면 기존처럼 재시도하지 않습니다. 정책을 명시한 경우에도 `LlmResponseError`와 400대 인증·입력 오류는 재시도하지 않습니다. 예제는 오류 객체 전체나 Authorization 헤더를 출력하지 않으므로 키가 노출되지 않습니다.

### 6.3 선택 사항: 자신의 제공자로 한 번 실행

이 명령은 외부 요청과 비용을 발생시킬 수 있습니다. 실행을 원하지 않으면 6.1 테스트까지만 수행합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cp .env.example .env
# .env에 OPENAI_API_KEY와 LLM_MODEL을 자신의 값으로만 설정
set -a
. ./.env
set +a
uv run python examples/volume01/error_handling.py
```

정상 응답이면 모델 텍스트가 출력됩니다. 실패하면 키를 포함하지 않는 한국어 안내가 출력됩니다. `.env`는 Git에 추가하지 않습니다.

## 7. 코드 설명

`UrllibJsonTransport`는 표준 라이브러리의 `TimeoutError`와 timeout 원인을 가진 `URLError`를 `LlmTimeoutError`로 변환합니다. 다른 `URLError`는 `LlmNetworkError`가 됩니다. 따라서 호출자는 제공자 라이브러리의 세부 예외 대신 플랫폼의 좁은 오류 계약을 처리합니다.

`LlmRemoteError`는 사람이 읽을 수 있는 안전한 메시지와 `status_code`를 분리합니다. `LlmClient._should_retry()`는 429·500·502·503·504, 네트워크 오류, 시간 초과만 선택합니다. `RetryPolicy`가 없거나 시도 한도에 도달하면 원래의 분류된 예외를 다시 발생시킵니다.

스트림은 한 글자라도 사용자에게 보낸 뒤 동일 요청을 재시도하면 중복 텍스트를 만들 수 있습니다. 따라서 `stream()`은 자동 재시도하지 않습니다. 스트리밍 재개 프로토콜과 중복 제거는 Volume 09의 상태·체크포인트 설계에서 명시적으로 다룹니다.

현재 Mock 단위 테스트의 출력은 다음과 유사합니다.

제공자가 요청을 거부했습니다. 상태 코드: 401

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `LLM provider request timed out` | `LLM_TIMEOUT_SECONDS`, 제공자 지연, 네트워크를 확인합니다. | 시간 제한을 서비스 SLO에 맞게 조정하고, 일시 오류에만 제한된 정책을 명시합니다. |
| 401 또는 403 | 키 누락·오류 또는 권한 부족입니다. | `.env`의 키와 프로젝트 권한을 확인합니다. 키를 터미널·로그·Git에 출력하지 않습니다. |
| 429 | 할당량 또는 속도 제한입니다. | 호출 빈도·할당량을 확인합니다. 정책을 사용한다면 제한된 백오프 후에도 실패를 호출자에게 전달합니다. |
| 400이 반복됨 | 모델명, 메시지 형식, 파라미터가 유효하지 않을 수 있습니다. | 요청을 수정합니다. 400은 자동 재시도 대상이 아닙니다. |
| 같은 답변이 두 번 보임 | 스트림을 임의로 재시도했을 수 있습니다. | 스트림 자동 재시도를 추가하지 말고, 중단·재개 정책을 별도 설계합니다. |
| 테스트가 느림 | 실제 `sleep`을 사용하는 테스트일 수 있습니다. | `sleeper`를 주입해 대기 시간을 기록하는 Mock으로 교체합니다. |

## 10. 응용 실습

1. `RetryPolicy(max_attempts=4, base_delay_seconds=0.25)`일 때 각 대기 시간을 계산하고, 최대 대기 시간이 서비스에 적절한지 기록합니다.
2. Mock 전송 계층에 429 뒤 200 응답을 추가해 재시도되는 테스트를 작성합니다.
3. 호출자 로그에 요청 원문 대신 요청 ID, 오류 분류, 상태 코드, 시도 횟수만 남기는 구조를 설계합니다.

## 11. 실무 적용

재시도 정책은 제공자별 제한, 서비스의 응답 시간 목표, 호출의 멱등성에 맞춰야 합니다. 429에는 제공자가 `Retry-After`를 제공할 수도 있습니다. 현재 간결한 HTTP 경계는 헤더를 노출하지 않으므로, 해당 지원이 필요해질 때는 무분별하게 대기 시간을 늘리지 말고 헤더·관찰 지표·테스트 계약을 함께 확장합니다.

운영에서는 오류 유형별 건수, 시도 횟수, 최종 실패율, 시간 초과율을 수집합니다. API 키, Authorization 헤더, 전체 프롬프트, 회사 문서는 이 지표나 오류 로그에 넣지 않습니다. 다음 장에서는 성공 응답의 토큰 사용량을 비용 추정과 연결합니다.

## 12. 과제

- **기본:** 401과 503이 다른 재시도 정책을 가져야 하는 이유를 설명합니다.
- **응용:** 재시도 3회와 지수 백오프의 장점·단점을 서비스 지연 관점에서 비교합니다.
- **심화:** 멱등성 키가 필요한 Tool 호출 사례를 하나 정하고, 중복 실행을 막는 요청·저장 구조와 Mock 테스트를 설계합니다.

## 13. 완료 체크리스트

- [ ] 시간 초과, 네트워크 오류, HTTP 오류, 응답 형식 오류를 구분할 수 있다.
- [ ] 429·5xx와 400·401의 재시도 여부가 다른 이유를 설명할 수 있다.
- [ ] `RetryPolicy`의 최대 시도 횟수와 지수 백오프를 설명할 수 있다.
- [ ] Mock 테스트로 재시도와 미재시도를 외부 호출 없이 확인했다.
- [ ] 스트리밍을 부분 출력 뒤 자동 재시도하면 안 되는 이유를 설명할 수 있다.
- [ ] 오류 메시지·로그에 키와 사용자 원문을 넣지 않아야 함을 확인했다.

## 14. 핵심 정리

안전한 LLM 오류 처리는 실패를 숨기지 않고 분류합니다. 이 프로젝트는 명시적으로 선택한 `RetryPolicy`에서만 일시적인 네트워크·시간 초과·429·5xx를 최대 5회까지 재시도합니다. 인증·입력·응답 형식 문제는 즉시 호출자에게 전달하고, 스트림은 중복 출력을 막기 위해 자동 재시도하지 않습니다.
