# 미니 프로젝트: 오프라인 검증 가능한 안전한 CLI 챗봇

## 1. 학습 목표

이 미니 프로젝트를 마치면 Volume 01에서 만든 설정 검증, 단일 완료 요청, 오류 처리, 토큰 사용량 계약, 제한된 대화 이력을 하나의 콘솔 프로그램으로 연결할 수 있습니다. 실제 API 키 없이도 오프라인 데모를 처음부터 실행하고, 그 실행 경로가 외부 네트워크를 사용하지 않는다는 것을 통합 테스트로 확인할 수 있습니다.

## 2. 왜 필요한가

개별 함수가 단위 테스트를 통과해도 사용자가 실제로 명령을 실행했을 때 프로그램이 시작되고 종료되는지는 별도로 확인해야 합니다. CLI 챗봇은 이후 Volume 05의 RAG 답변과 Volume 08의 Router가 붙을 공통 입구입니다. 따라서 이번 단계에서는 작은 기능을 늘리기보다 다음 안전 경계를 하나의 실행 흐름으로 검증합니다.

- 기본 라이브 모드는 환경 변수에서만 설정을 읽습니다.
- `--offline-demo`는 API 키, 계정, 네트워크 없이 결정론적으로 동작합니다.
- 빈 입력과 `/exit`, `/quit`은 제공자에 전송하지 않습니다.
- 성공한 사용자·Assistant 쌍만 다음 요청의 문맥으로 보관합니다.
- 오류 안내에는 원래 예외·API 키·사용자 입력을 넣지 않습니다.

## 3. 핵심 개념

**통합 테스트(integration test)** 는 여러 모듈을 함께 실행해 실제 사용 경로의 계약을 확인하는 테스트입니다. 여기서는 `subprocess`로 `examples/volume01/chat_cli.py --offline-demo`를 시작하고 표준 입력으로 질문과 `/exit`을 전달합니다. 이 경로는 `OfflineDemoClient`만 사용하므로 실제 LLM 제공자에 요청하지 않습니다.

**결정론적(deterministic) 데모** 는 같은 입력에 같은 출력을 반환하는 실행 방식입니다. 모델의 생성 결과를 평가하는 대신, CLI의 시작·입력·응답 표시·종료라는 프로그램 경계를 안정적으로 검사할 수 있습니다.

> [!WARNING]
> `--offline-demo`가 없는 기본 모드는 설정이 갖춰진 경우 선택한 LLM 제공자에 입력을 전송할 수 있습니다. 미니 프로젝트의 실행과 테스트에서는 기본 모드를 사용하지 않습니다. API 키, 회사 자료, 개인정보를 콘솔 입력이나 테스트 데이터에 넣지 않습니다.

## 4. 동작 구조

```text
터미널 또는 통합 테스트
        │ 표준 입력: 질문, /exit
        ▼
examples/volume01/chat_cli.py --offline-demo
        │
        ▼
OfflineDemoClient (외부 API 호출 없음)
        │
        ▼
run_chat_loop()
  ├── 시작 안내 출력
  ├── 질문에 데모 응답 출력
  └── /exit을 로컬에서 처리하고 종료
        │
        ▼
표준 출력 검증
```

## 5. 실습 환경

다음 파일은 이미 같은 AI 업무 처리 플랫폼 프로젝트 안에 있습니다.

- `src/ai_platform/llm/chat.py`: 이력과 안전한 콘솔 입출력 루프입니다.
- `examples/volume01/chat_cli.py`: 라이브 모드와 오프라인 데모를 선택하는 실행 파일입니다.
- `tests/integration/test_volume01_chat_cli.py`: 오프라인 CLI를 별도 프로세스로 실행하는 통합 테스트입니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cd ~/projects/ai-platform-engineering-book
uv sync --all-groups
```

이 명령은 프로젝트와 검사 도구를 준비합니다. Windows에서 WSL을 쓰는 경우 Windows 경로가 아니라 WSL에 복제한 저장소 경로에서 실행합니다.

## 6. 단계별 실습

### 6.1 오프라인 챗봇을 처음부터 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
printf 'AI Platform이란 무엇인가요?\n/exit\n' | uv run python examples/volume01/chat_cli.py --offline-demo
```

`printf`는 질문과 종료 명령을 차례대로 표준 입력에 전달합니다. `--offline-demo`가 있으므로 `.env`, API 키, 네트워크가 필요 없습니다. 출력의 데모 응답에는 방금 입력한 질문이 표시되고, 마지막에는 `대화를 마칩니다.`가 표시되어야 합니다.

### 6.2 실행 경계를 통합 테스트로 검사

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/integration/test_volume01_chat_cli.py -q
```

테스트는 별도 Python 프로세스가 종료 코드 0으로 끝나는지, 시작 안내·오프라인 데모 응답·로컬 종료 안내가 모두 있는지 확인합니다. 테스트는 `--offline-demo`만 호출하므로 외부 API 요청과 비용이 없습니다.

### 6.3 Volume 01의 전체 품질 검사 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
bash scripts/run_all_tests.sh
```

이 명령은 Ruff, mypy, 문서·링크·코드 블록·비밀값 검사와 전체 pytest를 순서대로 실행합니다. 어느 하나라도 실패하면 다음 Volume으로 진행하지 말고 실패한 검사와 관련된 파일부터 확인합니다.

## 7. 코드 설명

통합 테스트는 `sys.executable`을 사용합니다. 따라서 테스트를 실행한 `uv` 가상환경과 같은 Python으로 CLI를 실행합니다. `subprocess.run()`에는 질문과 `/exit`만 `input`으로 전달하고, `capture_output=True`로 프로그램의 표준 출력을 검사합니다.

```python
result = subprocess.run(
    [sys.executable, str(CHAT_CLI), "--offline-demo"],
    cwd=ROOT,
    input="AI Platform이란 무엇인가요?\n/exit\n",
    text=True,
    capture_output=True,
    check=True,
    timeout=10,
)

assert "오프라인 데모 응답" in result.stdout
assert "대화를 마칩니다." in result.stdout
```

`cwd=ROOT`는 실행 위치를 저장소 루트로 고정합니다. `timeout=10`은 종료 명령 처리 오류로 테스트가 무한 대기하는 상황을 빠르게 발견합니다. `check=True`는 CLI가 0이 아닌 종료 코드를 반환하면 테스트가 실패하게 합니다. 테스트 출력에는 API 키를 전달하거나 검사하지 않습니다.

## 8. 정상 실행 결과

```text
사용자> 대화를 마칩니다.
```


## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `No module named ai_platform` | 가상환경을 준비하지 않았거나 저장소 밖에서 실행했습니다. | 저장소 루트에서 `uv sync --all-groups` 후 `uv run ...` 명령을 사용합니다. |
| 테스트가 시간 초과됨 | `/exit`이 전달되지 않았거나 CLI 루프가 종료 명령을 처리하지 못했습니다. | 입력 문자열에 줄바꿈 포함 `/exit\n`이 있는지, `run_chat_loop()`의 종료 분기가 유지되는지 확인합니다. |
| 라이브 제공자 오류가 표시됨 | `--offline-demo`를 빼고 실행했습니다. | API 키 없는 학습과 검증에는 항상 `--offline-demo`를 붙입니다. |
| 출력이 예시와 한 줄씩 다름 | 파이프 입력은 대화형 터미널과 프롬프트 표시 방식이 다릅니다. | 문장 전체의 줄 위치가 아니라 시작 안내, 데모 응답, 종료 안내가 모두 있는지 확인합니다. |
| `.env`를 만들고 싶음 | 라이브 호출을 시도하려는 상태입니다. | 이번 미니 프로젝트에는 필요 없습니다. 라이브 실습은 05장을 따르고 `.env`를 Git에 추가하지 않습니다. |

## 10. 응용 실습

1. 통합 테스트에 `/quit` 입력 경로를 추가하고, 제공자 연결 없이 종료 문구가 출력되는지 확인합니다.
2. `ConversationHistory(max_turns=2)`를 주입하는 별도 CLI 실행 함수를 설계하고, 세 번째 성공 응답 뒤 가장 오래된 턴이 사라지는 단위 테스트를 작성합니다.
3. 오프라인 응답에 전체 질문을 기록하지 않고 길이만 표시하도록 바꿀 때, 학습 확인 가능성과 로그 최소화 사이의 장단점을 문서화합니다.

## 11. 실무 적용

운영용 CLI의 통합 테스트는 실제 모델의 답변 품질을 보장하지 않습니다. 대신 시작 실패, 환경 경로 오류, 입력 종료, 민감정보 노출 같은 프로그램 경계의 회귀를 빠르게 잡습니다. 모델 품질은 Volume 10의 Golden Dataset과 평가 지표로 별도로 측정해야 합니다.

서비스가 여러 인스턴스로 확장되면 메모리 이력만으로는 세션이 유지되지 않습니다. 그때는 사용자별 접근 제어, 보존 기한, 삭제 요청, 암호화와 관측 가능성을 설계한 뒤 안전한 저장소를 선택합니다. 다음 Volume에서는 이 콘솔 경계에 Prompt 템플릿과 입력 검증을 추가합니다.

## 12. 과제

- **기본:** 오프라인 데모를 라이브 모드와 분리해야 하는 이유를 외부 전송과 재현성 관점에서 설명합니다.
- **응용:** 통합 테스트와 단위 테스트가 각각 발견할 수 있는 실패 사례를 두 가지씩 작성합니다.
- **심화:** 여러 CLI 세션의 이력을 영속화하는 요구사항을 가정하고, 저장하면 안 되는 데이터와 보존·삭제 정책을 설계합니다.

## 13. 완료 체크리스트

- [ ] `--offline-demo`로 API 키와 네트워크 없이 챗봇을 실행했다.
- [ ] 질문 뒤 `/exit`이 제공자 요청이 아닌 로컬 종료임을 확인했다.
- [ ] 통합 테스트가 별도 Python 프로세스로 CLI를 실행함을 설명할 수 있다.
- [ ] 테스트의 시간 제한과 종료 코드 검사가 필요한 이유를 설명할 수 있다.
- [ ] 기본 라이브 모드가 외부 전송·비용을 발생시킬 수 있음을 이해한다.
- [ ] 테스트 데이터와 출력에 실제 API 키·회사 문서·개인정보를 넣지 않았다.

## 14. 핵심 정리

Volume 01의 미니 프로젝트는 단순한 CLI 챗봇을 안전한 실행 경계로 완성합니다. 오프라인 데모는 외부 제공자와 분리되어 재현 가능하며, 통합 테스트는 사용자가 실제로 실행하는 시작·입력·응답·종료 흐름을 검증합니다. 이후 Volume은 이 검증된 입구에 Prompt, Tool, RAG, Router, 상태형 Workflow를 차례로 연결합니다.
