# LLM·Transformer·Token: 텍스트가 요청과 응답이 되기까지

## 1. 학습 목표

이 장을 마치면 AI, 머신러닝, 딥러닝, 생성형 AI, LLM의 포함 관계를 설명할 수 있습니다. 또한 Tokenizer가 텍스트를 토큰으로 나누는 방식, Transformer가 문맥을 참고하는 개요, 입력·출력 토큰이 Context Window를 함께 사용한다는 점을 안전한 CLI의 요청 흐름과 연결할 수 있습니다.

- AI, 머신러닝, 딥러닝, 생성형 AI, LLM의 역할과 범위를 구분한다.
- Token과 Tokenizer가 글자 수·단어 수와 항상 같지 않은 이유를 설명한다.
- Transformer의 attention이 문장 안의 관련 정보를 함께 참고한다는 수준에서 설명한다.
- System, User, Assistant 메시지와 입력·출력 토큰이 Context Window 예산을 함께 사용함을 설명한다.
- 실제 API 키·네트워크 없이 Volume 01의 오프라인 CLI와 Mock Client 계약을 실행한다.

## 2. 왜 필요한가

LLM API에 문자열 하나를 전달하는 코드는 짧지만, 모델이 보는 요청은 짧은 문자열 하나가 아닙니다. System 메시지, 이전 대화, 사용자 질문, 검색 문서, Tool 결과가 모두 입력 토큰이 될 수 있고, 생성할 답변도 같은 Context Window의 공간을 사용합니다. 이 구조를 모르고 대화 이력이나 문서를 계속 붙이면 응답이 잘리거나 비용과 지연 시간이 예측보다 커질 수 있습니다.

모델이 문장을 생성한다고 해서 사실·최신 정보·권한을 보장하는 것은 아닙니다. 이 장은 모델 내부를 구현하는 대신, **토큰 예산과 메시지 경계**를 이해하여 다음 장의 API 호출과 이후 RAG·Tool 설계를 안전하게 준비하는 데 집중합니다.

> [!WARNING]
> 실제 API 키, 회사 문서, 개인정보를 토큰 수를 세어 보겠다는 이유로 코드·콘솔·테스트에 넣지 마세요. 이 장의 실행 경로는 `--offline-demo`와 Mock 테스트이며 네트워크와 API 키를 사용하지 않습니다. 오프라인 데모의 응답은 사실 답변이 아니라 CLI 계약을 위한 결정론적 문자열입니다.

## 3. 핵심 개념

**AI(Artificial Intelligence)** 는 인식, 예측, 계획, 언어 처리처럼 지능적 행동을 보이게 하는 넓은 기술 분야입니다. **머신러닝(Machine Learning)** 은 사람이 모든 규칙을 직접 작성하는 대신 데이터에서 패턴을 학습하는 AI의 한 방법입니다. **딥러닝(Deep Learning)** 은 여러 층의 신경망으로 복잡한 패턴을 학습하는 머신러닝의 한 분야입니다.

**생성형 AI(Generative AI)** 는 학습한 패턴을 이용해 새 텍스트, 이미지, 코드, 음성 등의 후보를 생성합니다. **대규모 언어 모델(Large Language Model, LLM)** 은 대량의 텍스트로 학습되어 다음 토큰의 확률을 예측하는 생성형 AI 모델입니다. LLM은 자연어 요약·분류·초안에 도움을 주지만 데이터베이스 조회, 정확한 계산, 권한 판정, 최신 사실을 대신하지는 않습니다.

```text
AI
└── 머신러닝
    └── 딥러닝
        └── 생성형 AI
            └── LLM: 텍스트 토큰의 다음 후보를 예측
```

**토큰(Token)** 은 모델이 읽고 생성하는 처리 단위입니다. 한글 글자, 공백으로 나눈 단어, 영어 단어와 일대일로 대응하지 않습니다. 제공자와 모델별 **Tokenizer** 는 같은 문장도 서로 다른 토큰 목록으로 나눌 수 있습니다. 따라서 `문자 수 ÷ 일정한 값`은 대략적인 사전 추정일 뿐 정확한 청구·한도 판단에는 해당 모델의 Tokenizer 또는 제공자 사용량이 필요합니다.

**Transformer** 는 문장 안의 토큰들이 서로 어떤 관계가 있는지 살피는 신경망 구조입니다. attention은 현재 처리 중인 토큰이 다른 토큰 중 무엇을 더 참고할지 가중치를 두는 개요적 메커니즘입니다. 예를 들어 “민지는 보고서를 읽고 그녀는 요약했다”에서 “그녀”를 해석할 때 앞선 “민지”와의 관계를 참고합니다. 이 설명은 Transformer를 구현하거나 내부 점수를 해석하는 방법이 아니며, 모델의 사실성·공정성·보안을 보장하지도 않습니다.

**Context Window** 는 한 요청에서 모델이 함께 고려할 수 있는 토큰의 최대 예산입니다. 입력 토큰과 출력 토큰은 별개로 과금될 수 있어도, 요청을 처리할 때는 함께 공간을 차지합니다. 최대 출력 토큰을 크게 잡으면 답변 공간은 늘지만 입력에 남는 공간과 비용 상한이 달라집니다.

## 4. 동작 구조

```text
텍스트와 메시지 역할
  System: 서비스 규칙
  User: 현재 질문
  Assistant: 성공한 이전 답변
             │
             ▼
Tokenizer ──► 토큰 ID 목록
             │
             ▼
Transformer ──► 문맥 속 토큰 관계를 참고해 다음 토큰 후보 계산
             │
             ▼
생성 파라미터를 적용해 출력 토큰을 순차 생성
             │
             ▼
LlmResponse(content, usage)
```

한 요청의 예산은 아래처럼 생각할 수 있습니다. 검색 문서와 Tool 결과는 이후 Volume에서 추가되지만, 들어오는 순간 사용자 질문과 마찬가지로 입력 예산을 차지합니다.

```text
입력: System + 이전 User/Assistant 턴 + 현재 User + 검색 문서 + Tool 결과
출력: 새 Assistant 응답

입력 토큰 + 출력 토큰 ≤ 모델의 Context Window
```

`ConversationHistory`는 최근 성공 턴만 보관하여 무한히 입력을 늘리지 않습니다. 그러나 턴 수 제한은 정확한 토큰 제한이 아닙니다. 실제 서비스에서는 모델별 Tokenizer, 현재 입력 길이, 검색 문서 수, `max_output_tokens`, 비용 예산을 함께 정책으로 관리해야 합니다.

## 5. 실습 환경

이 장은 새 모델을 학습하거나 라이브 API를 호출하지 않습니다. 현재 저장소의 안전한 실행 경계를 사용합니다.

- `src/ai_platform/llm/client.py`: `ChatMessage`, 생성 파라미터, 응답 사용량의 요청 계약입니다.
- `src/ai_platform/llm/chat.py`: System 메시지와 성공한 최근 턴을 요청에 넣는 이력 경계입니다.
- `examples/volume01/chat_cli.py`: `--offline-demo`에서 API 키와 네트워크 없이 동작하는 CLI입니다.
- `tests/unit/test_llm_client.py`: Mock 전송으로 메시지·생성 파라미터·사용량을 검사합니다.
- `tests/unit/test_chat.py`: Mock Client로 이력 한도와 로컬 종료를 검사합니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cd ~/projects/ai-platform-engineering-book
uv sync --all-groups
```

Windows에서 Git Bash를 사용한다면 현재 저장소 경로로 이동해 같은 `uv` 명령을 실행합니다. 기본 검증에는 `.env` 작성이나 API 키 설정이 필요하지 않습니다.

## 6. 단계별 실습

### 6.1 토큰 예산이 필요한 사용자 흐름을 오프라인으로 실행

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
printf 'Context Window와 Token의 관계를 설명해 주세요.\n/exit\n' | \
  uv run python examples/volume01/chat_cli.py --offline-demo
```

출력의 데모 응답에는 입력 문장이 다시 나타납니다. 이 결과는 Tokenizer가 실제 토큰 수를 출력했다는 뜻이 아닙니다. `--offline-demo`가 질문을 받고 `/exit`을 모델에 보내지 않고 종료하는지 확인하는 실행입니다. 네트워크와 API 키를 사용하지 않습니다.

### 6.2 Mock으로 메시지와 이력 경계 검사

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/unit/test_llm_client.py tests/unit/test_chat.py -q
```

첫 테스트 파일은 `system`, `user`, `assistant` 역할, 생성 파라미터, 응답의 `prompt_tokens`와 `completion_tokens` 정규화를 검증합니다. 두 번째 파일은 System 메시지를 유지하면서 오래된 성공 턴을 제거하고, 실패한 질문과 `/exit`을 이력·제공자 요청에서 제외하는지 검증합니다. 둘 다 실제 제공자에 요청하지 않습니다.

### 6.3 요청에 포함되는 항목을 직접 분류

다음 요청에서 각 항목이 입력 토큰인지, 출력 토큰인지, 또는 로컬 처리인지 분류합니다.

```text
System: "근거가 없으면 모른다고 답하세요."
이전 User: "Token은 무엇인가요?"
이전 Assistant: "모델의 처리 단위입니다."
현재 User: "Context Window와 관계는요?"
/exit
```

- 앞의 네 메시지는 다음 `complete()` 요청을 만들면 입력 토큰 후보입니다.
- 새 Assistant 답변은 출력 토큰 후보입니다.
- `/exit`은 `is_exit_command()`가 로컬에서 처리하므로 모델 요청과 토큰 사용량에 포함되지 않아야 합니다.

## 7. 코드 설명

`src/ai_platform/llm/client.py`의 `ChatMessage`는 허용된 역할과 비어 있지 않은 내용을 먼저 검사합니다. `LlmClient.complete()`는 메시지를 OpenAI 호환 JSON의 `messages` 목록으로 만들고, 제공자가 응답한 `usage.prompt_tokens`와 `usage.completion_tokens`를 `TokenUsage(input_tokens, output_tokens)`로 정규화합니다. 제공자가 사용량을 주지 않으면 현재 계약은 두 값을 `0`으로 둡니다. 이것은 무료 호출의 증거가 아니라 **사용량 미수신 여부를 호출자가 별도로 판단해야 하는 신호**입니다.

`src/ai_platform/llm/chat.py`의 `ConversationHistory.messages_for()`는 System 메시지, 성공한 최근 사용자·Assistant 쌍, 새 User 메시지를 새 목록으로 반환합니다. `record_success()`는 응답이 성공한 뒤에만 쌍을 저장합니다. 그러므로 실패한 질문이 다음 요청의 문맥 또는 토큰 예산에 몰래 섞이지 않습니다.

정확한 토큰 수는 이 모듈이 문자열 길이로 계산하지 않습니다. 모델별 Tokenizer와 제공자 사용량이 다를 수 있기 때문입니다. 호출 전 예산을 보호하려면 넉넉한 보수적 상한, 문서 길이 제한, `max_output_tokens`, 대화 이력 턴 수, 제공자 문서의 Context Window를 함께 사용해야 합니다.

## 8. 정상 실행 결과

6.1의 출력은 운영체제의 프롬프트 표시에 따라 공백과 줄 위치가 다를 수 있지만 다음 문구를 포함합니다.

```text
AI 업무 처리 플랫폼 챗봇입니다. 종료하려면 /exit 또는 /quit을 입력하세요.
사용자> AI> 오프라인 데모 응답: 'Context Window와 Token의 관계를 설명해 주세요.' 요청을 기록했습니다.
사용자> 대화를 마칩니다.
```

6.2는 pytest 버전에 따라 시간과 테스트 개수가 달라도 `passed`로 끝나야 합니다. 이 결과가 모델 답변의 사실성을 보장하지는 않습니다. 메시지 역할, 이력, 요청 형식의 오프라인 계약이 유지됨을 뜻합니다.

## 10. 응용 실습

1. `ConversationHistory(max_turns=2)`에서 세 번 성공한 뒤 네 번째 요청에 어떤 메시지가 남는지 표로 작성하고, 왜 가장 오래된 **완료된 쌍**을 같이 제거해야 하는지 설명합니다.
2. 같은 사용자 질문에 System 메시지 1개, 이전 대화 2턴, 검색 문서 3개를 넣는 상황을 가정합니다. 각 항목을 줄이면 답변 공간·근거 품질·비용이 어떻게 달라질지 비교합니다. 실제 문서나 라이브 API는 사용하지 않습니다.
3. 모델별 Tokenizer가 다를 수 있다는 사실을 고려하여 호출 전 토큰 상한을 보수적으로 검사하는 함수의 입력·출력·실패 정책을 설계합니다. 정확한 토큰 계산 실패를 0으로 처리하지 않는 이유를 포함합니다.

## 11. 실무 적용

운영 시스템에서는 Tokenizer와 모델 버전을 함께 관리해야 합니다. 모델을 바꾸면 Context Window, 가격, 사용량 반환 형식, 토큰 분할이 바뀔 수 있습니다. 배포 전에 대표 입력·대화 이력·검색 문서 조합으로 최대 요청 크기와 출력 상한을 점검하고, 실제 응답에서 받은 모델명·입출력 사용량·지연 시간처럼 최소한의 관측 정보를 기록합니다. API 키, Authorization 헤더, 전체 프롬프트, 개인정보는 로그에 넣지 않습니다.

RAG의 문서, Tool Calling의 도구 결과, Agent의 상태도 모두 문맥으로 들어올 수 있습니다. 이들은 System 정책이 아니라 신뢰되지 않은 데이터로 분리해야 하며, 길이 제한·출처·권한·사람 승인은 토큰 예산과 별개로 설계해야 합니다. 다음 장에서는 이 메시지·토큰 개념을 실제 API 설정과 최초 호출 경계에 연결합니다.

## 12. 과제

- **기본:** AI, 머신러닝, 딥러닝, 생성형 AI, LLM의 포함 관계를 그리고 LLM이 최신 사실을 보장하지 않는 이유를 설명합니다.
- **응용:** Tokenizer가 글자 수와 다른 결과를 낼 수 있는 이유와, 입력·출력 토큰이 Context Window 및 비용에 미치는 영향을 설명합니다.
- **심화:** System 메시지, 대화 이력, 검색 문서, Tool 결과, 최대 출력 토큰으로 구성된 Context Window 예산 정책을 설계합니다. 길이 초과 때 제거·요약·거부 중 어느 정책을 적용할지와 Mock 테스트 사례를 작성합니다.

## 13. 완료 체크리스트

- [ ] AI, 머신러닝, 딥러닝, 생성형 AI, LLM의 관계를 설명할 수 있다.
- [ ] Token과 Tokenizer가 글자 수·단어 수와 같지 않을 수 있음을 설명할 수 있다.
- [ ] Transformer가 토큰 사이의 문맥 관계를 참고한다는 개요를 설명할 수 있다.
- [ ] System, User, Assistant 메시지의 책임을 구분했다.
- [ ] 입력 토큰과 출력 토큰이 같은 Context Window 예산을 함께 사용함을 설명할 수 있다.
- [ ] 턴 제한이 정확한 토큰 제한을 대체하지 않는 이유를 설명할 수 있다.
- [ ] `--offline-demo`와 Mock 테스트를 API 키·네트워크 없이 실행했다.
- [ ] 모델 응답을 최신 사실·권한·위험 작업의 승인 근거로 사용하지 않는다.
- [ ] 다음 장 [환경 설정](04-environment-setup.md)으로 이어지는 학습 순서를 확인했다.

## 14. 핵심 정리

LLM은 Tokenizer로 나눈 토큰의 다음 후보를 예측하는 생성형 AI이며, Transformer는 문맥 안의 토큰 관계를 참고하는 구조입니다. 요청의 System 메시지, 대화 이력, 사용자 입력, 검색·도구 결과와 새 출력은 모두 제한된 Context Window와 비용에 영향을 줍니다. 따라서 역할을 분리하고 이력·출력 상한을 정책으로 관리하며, 오프라인 CLI와 Mock 테스트로 요청 경계를 먼저 검증해야 합니다. 다음 장에서는 이 이해를 환경 변수와 안전한 최초 API 호출에 연결합니다.
