# LLM 기초: Transformer, Token, 컨텍스트 윈도우

## 1. 학습 목표

이 장을 마치면 다음을 할 수 있어야 합니다.

- AI, 머신러닝(Machine Learning), 딥러닝(Deep Learning), 생성형 AI(Generative AI), 대규모 언어 모델(Large Language Model, LLM)의 포함 관계를 설명한다.
- Transformer의 토큰 처리와 Attention의 목적을 고수준에서 설명한다.
- 토큰(Token), 토크나이저(Tokenizer), 입력·출력 토큰, 컨텍스트 윈도우(Context Window)를 구분한다.
- System, User, Assistant 메시지와 검색 문서·도구 결과가 같은 입력 예산을 공유함을 설명한다.
- 확인한 토큰 수와 출력 예약량으로 요청 계획이 컨텍스트 윈도우에 맞는지 오프라인 코드로 점검한다.
- 토큰 수가 글자 수와 다르고, 추정값을 실제 제공자 토크나이저 값으로 대체해야 하는 이유를 설명한다.

## 2. 왜 필요한가

AI는 사람이 하던 지능 작업을 다루는 넓은 분야입니다. 머신러닝은 데이터에서 규칙을 학습하는 AI의 한 방법이고, 딥러닝은 여러 신경망 층을 사용하는 머신러닝의 한 종류입니다. 생성형 AI는 새 텍스트·이미지·코드를 만드는 모델을 가리키며, LLM은 그중 텍스트 토큰을 생성하는 모델입니다.

AI 업무 처리 플랫폼은 대화가 길어질수록 System 정책, 사용자 요청, 이전 Assistant 응답, 검색 문서, Tool 결과를 함께 보냅니다. 이 항목은 모두 컨텍스트 윈도우를 차지합니다. 입력을 무작정 늘리면 요청이 거절되거나, 남은 출력 공간이 부족해 답변이 중간에 끝날 수 있습니다. 따라서 모델 호출 전에 **입력 토큰과 예약 출력 토큰을 합산**하는 계획이 필요합니다.

> [!WARNING]
> 글자 수나 공백으로 계산한 값은 모델 토크나이저의 실제 토큰 수가 아닙니다. 모델·버전·언어에 따라 분할 결과가 달라집니다. 이 장의 코드는 이미 확인한 토큰 수를 검증하는 예산 도구이며, 실제 요청 전에는 선택한 제공자의 토크나이저 또는 응답 사용량을 기준으로 값을 확인해야 합니다.

## 3. 핵심 개념

- **Transformer:** 토큰들의 관계를 Attention으로 계산해 다음 토큰의 확률을 예측하는 신경망 구조입니다. 이 장에서는 내부 수식을 구현하지 않고, 입력 길이와 문맥의 관계를 다룹니다.
- **Attention:** 현재 처리할 토큰이 다른 토큰을 얼마나 참고할지 가중치를 두는 방식입니다. 긴 입력도 항상 같은 품질로 처리된다는 보장은 없습니다.
- **토큰과 토크나이저:** 토크나이저는 텍스트를 모델이 처리할 토큰으로 나눕니다. 한글 한 글자, 영어 한 단어, 공백이 각각 정확히 하나의 토큰이라는 규칙은 없습니다.
- **입력 토큰:** System·User·Assistant 메시지, 검색 문서, Tool 결과처럼 모델에 전달하는 모든 텍스트가 차지하는 토큰입니다.
- **출력 토큰:** 모델이 생성하는 답변의 토큰입니다. `max_output_tokens`는 출력의 상한을 요청하지만, 컨텍스트 윈도우 안에 둘 공간도 미리 남겨야 합니다.
- **컨텍스트 윈도우:** 한 요청에서 모델이 함께 처리할 수 있는 입력과 출력 토큰의 최대 범위입니다. 모델별 한도가 다르므로 모델 변경 시 정책도 다시 확인합니다.
- **환각(Hallucination)과 최신성:** 컨텍스트를 길게 넣어도 답변의 사실성은 자동으로 보장되지 않습니다. 이후 Volume의 RAG, 출처, 검증, 평가가 별도로 필요합니다.

## 4. 동작 구조

```text
AI
└─ 머신러닝
   └─ 딥러닝
      └─ 생성형 AI
         └─ LLM: 다음 토큰 예측

System 정책 + 대화 이력 + User 요청 + RAG 문서 + Tool 결과
                             │
                             ▼
                       토크나이저
                             │ 확인한 입력 토큰 수
                             ▼
┌──────────────────── 컨텍스트 윈도우 ────────────────────┐
│ 입력 토큰                           │ 예약 출력 토큰    │
│ (모든 전달 문맥의 합)                │ (답변 공간)       │
└────────────────────────────────────────────────────────┘
                             │
                             ▼
                    Transformer / Attention
                             │
                             ▼
                       다음 토큰을 순차 생성
```

`ContextBudget`은 토크나이저를 대신하지 않습니다. 모델별 토크나이저에서 얻은 입력 토큰 수를 받아, 예약한 출력까지 포함한 요청 계획이 한도에 맞는지 결정론적으로 판정합니다. 이 검사는 외부 API·API 키·네트워크 없이 수행됩니다.

## 5. 실습 환경

이 장은 표준 라이브러리와 기존 프로젝트 패키지만 사용합니다.

- `src/ai_platform/llm/context.py`: 컨텍스트 윈도우, 출력 예약량, 입력 토큰 수를 검증합니다.
- `examples/volume01/token_budget.py`: 두 요청 계획의 남은 토큰 예산을 비교합니다.
- `tests/unit/test_context.py`: 정상·초과·잘못된 입력을 외부 호출 없이 검사합니다.
- `src/ai_platform/llm/client.py`: 다음 장들에서 실제 응답의 `TokenUsage`를 받는 안전한 호출 경계입니다.

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
cd ~/projects/ai-platform-engineering-book
uv sync --all-groups
```

`uv sync --all-groups`는 프로젝트 가상환경과 검사 도구를 준비합니다. 이 장의 기본 실습에는 `.env`, API 키, 인터넷 연결이 필요하지 않습니다.

## 6. 단계별 실습

### 6.1 컨텍스트 예산을 오프라인으로 계산

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run python examples/volume01/token_budget.py
```

예제는 컨텍스트 윈도우 2,048토큰 중 400토큰을 출력용으로 예약합니다. 입력이 1,500토큰이면 148토큰이 남아 가능하고, 입력이 1,800토큰이면 총 2,200토큰이 되어 152토큰을 초과합니다. 숫자는 설명용으로 고정했으며 실제 토큰화 결과가 아닙니다.

### 6.2 초과 요청을 전송 전에 막는 단위 테스트

```bash
# 실행 위치: WSL Ubuntu 또는 Linux 터미널, 저장소 루트
uv run pytest tests/unit/test_context.py -q
```

테스트는 `require_fits()`가 100토큰 윈도우에서 입력 81토큰과 예약 출력 20토큰의 조합을 거부하는지 확인합니다. HTTP 전송 계층을 만들거나 실제 모델을 호출하지 않으므로 API 키·네트워크·비용이 필요하지 않습니다.

### 6.3 실제 토큰 수를 얻는 위치 구분

실서비스에서는 다음 순서로 연결합니다.

1. 선택한 모델의 토크나이저로 System 메시지, 이력, 사용자 입력, 검색 문서, Tool 결과의 토큰 수를 계산합니다.
2. 서비스 정책에 따라 출력 예약량을 정합니다. 짧은 분류 응답과 긴 보고서 생성의 예약량은 다를 수 있습니다.
3. `ContextBudget.require_fits()`로 요청을 점검합니다.
4. 초과하면 오래된 대화 이력을 요약하거나, 검색 문서 수·청크 길이를 줄이거나, 더 큰 컨텍스트 모델을 정책·비용 검토 뒤 선택합니다.
5. 실제 호출 뒤 제공자가 반환한 사용량을 기록하여 추정과 차이를 평가합니다.

4단계에서 문맥을 줄일 때 System 정책, 권한 정보, 인용에 필요한 출처를 임의로 제거하지 않습니다. 문맥 압축도 정보 손실과 환각 위험을 만들 수 있으므로 다음 Volume의 RAG 평가와 함께 검증합니다.

## 7. 코드 설명

`ContextBudget(context_window_tokens=2048, reserved_output_tokens=400)`은 입력에 쓸 수 있는 최대치 1,648토큰을 계산합니다. `assess(input_tokens)`는 입력과 예약 출력을 합산한 `ContextAssessment`를 돌려줍니다. `remaining_tokens`가 음수여도 값을 보존하므로, 얼마나 초과했는지 로그와 사용자 안내에 사용할 수 있습니다.

`require_fits(input_tokens)`는 초과 계획을 예외로 바꾸는 호출 전 보호 장치입니다. 오류에는 가능한 입력 상한만 포함하고 요청 원문·API 키는 포함하지 않습니다. 정수 이외의 값, 음수, 불리언, 출력 예약량이 컨텍스트 윈도우보다 큰 설정은 모두 요청 전에 거부합니다.

이 코드는 텍스트를 임의의 비율로 토큰화하지 않습니다. 부정확한 추정으로 안전하다고 판정하는 것보다, 토크나이저 또는 제공자 사용량이라는 출처를 호출자가 명시하게 하는 편이 안전하기 때문입니다.

## 8. 정상 실행 결과

6.1 명령은 다음 내용을 포함합니다.

```text
요약 요청: 입력=1500, 출력 예약=400, 계획 합계=1900, 남은 예산=148, 판정=가능
긴 검색 문맥 요청: 입력=1800, 출력 예약=400, 계획 합계=2200, 남은 예산=-152, 판정=초과
```

6.2의 pytest 출력은 설치된 버전에 따라 시간은 달라질 수 있지만 `passed`로 끝나야 합니다. 초과 사례가 테스트 실패가 아니라 `fits is False` 또는 `ContextBudgetError`로 확인되는 것이 정상입니다.

## 9. 오류 해결

| 증상 | 원인 확인 | 해결 |
|---|---|---|
| `No module named ai_platform` | 저장소 루트가 아니거나 `uv run`을 생략했을 수 있습니다. | 저장소 루트에서 `uv sync --all-groups` 후 `uv run python ...`을 사용합니다. |
| `reserved_output_tokens must not exceed context_window_tokens` | 출력 예약량이 모델의 전체 한도보다 큽니다. | 모델의 실제 컨텍스트 한도를 확인하고, 작업에 맞는 양의 윈도우와 그 이하의 예약량을 설정합니다. |
| `input_tokens must be at most ...` | 입력과 예약 출력을 합친 계획이 한도를 넘었습니다. | 이력·검색 문서를 정책적으로 줄이거나 요약하고, 다시 토큰을 확인합니다. 단순히 출력 예약량을 0으로 만들지 않습니다. |
| 글자 수는 짧은데 요청이 거절됨 | 모델별 토크나이저와 메시지 포맷의 오버헤드가 반영되지 않았을 수 있습니다. | 글자 수 추정을 실제 토크나이저 계산으로 교체하고, System 메시지·이력·도구 결과도 포함합니다. |
| 입력을 줄였는데 답변 근거가 사라짐 | 문맥 축소 시 인용·정책 문서를 제거했을 수 있습니다. | 출처와 시스템 정책을 보존하는 축소 규칙을 만들고, 다음 Volume의 검색 평가로 품질을 확인합니다. |

## 10. 응용 실습

1. `tests/unit/test_context.py`에 컨텍스트 윈도우 128토큰, 예약 출력 0토큰, 입력 128토큰이 정확히 맞는 사례를 추가합니다. 네트워크 호출은 추가하지 않습니다.
2. 고객 문의 분류 작업과 장애 보고서 요약 작업에 각각 다른 출력 예약량을 선택하고, 그 근거를 답변 길이·비용·잘림 위험으로 설명합니다.
3. RAG 문서 세 개의 토큰 수가 각각 300, 500, 700이고 대화 이력과 System 정책이 400토큰이라고 가정합니다. 2,048토큰 윈도우에서 300토큰을 출력용으로 예약할 때 어느 문서를 우선 줄일지, 출처 보존 정책과 함께 설계합니다.

## 11. 실무 적용

컨텍스트 예산은 Prompt, RAG, Tool Calling, Agent가 연결될수록 중요한 공통 정책입니다. 요청마다 모델 식별자, 토크나이저 버전, 입력 토큰, 출력 예약량, 실제 사용량을 비밀값·원문 개인정보 없이 기록하면 한도 초과와 비용 증가를 관찰할 수 있습니다.

긴 문맥이 항상 더 정확한 답변을 만들지는 않습니다. 관련 없는 문서를 많이 넣으면 주의가 분산되고 지연·비용도 증가합니다. 따라서 검색 결과의 수와 순서, 대화 이력 보존, 출력 상한을 평가 데이터로 조정합니다. 라이브 모델 호출은 이 장의 범위 밖이며, 기본 검증은 계속 오프라인 코드와 테스트로 수행합니다.

## 12. 과제

- **기본:** 토큰과 글자 수가 일대일 대응하지 않는 이유, 그리고 입력 토큰에 포함되는 항목 네 가지를 설명합니다.
- **응용:** 컨텍스트 윈도우 8,192토큰과 출력 예약 1,024토큰에서 입력 가능한 최대 토큰 수를 계산하고, 그 값을 코드의 `available_input_tokens` 결과로 확인합니다.
- **심화:** 모델별 컨텍스트 한도와 토크나이저 버전을 정책으로 관리하는 자료 구조를 설계합니다. 모델 변경·RAG 문서 추가·대화 이력 요약 시 어떤 회귀 테스트가 필요한지도 적습니다.

## 14. 핵심 정리

LLM은 토크나이저가 분할한 토큰을 Transformer와 Attention으로 처리하며 다음 토큰을 생성합니다. 한 요청의 System 정책, 이력, 사용자 입력, 검색 문서, Tool 결과, 출력은 하나의 컨텍스트 윈도우를 공유합니다. `ContextBudget`으로 확인한 입력과 예약 출력을 먼저 점검하면 한도 초과를 외부 호출 전에 드러낼 수 있습니다. 다음 장에서는 이 오프라인 검증 경계를 유지한 채 프로젝트 환경을 준비합니다.
