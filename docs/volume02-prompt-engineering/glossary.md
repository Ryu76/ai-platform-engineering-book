# Volume 02 주요 용어집

## 목적

이 용어집은 Volume 02에서 처음 다루는 Prompt Engineering 용어를 한곳에 모읍니다. 용어를 안다고 해서 Prompt의 안전성이나 모델 응답의 정확성이 보장되지는 않습니다. 각 용어의 계약, 검증, 권한 경계를 함께 확인해야 합니다.

## Prompt 설계

| 용어 | 정의 | 이 권에서의 경계 |
|---|---|---|
| 프롬프트(Prompt) | 모델 또는 후속 처리 계층에 전달할 요청 계약입니다. | 문자열 하나로 관리하지 않고 구성 요소와 버전을 분리합니다. |
| 지시문(Instruction) | 수행할 작업을 명시하는 서비스 소유 요구입니다. | 신뢰되지 않은 사용자 입력이 지시문을 바꾸게 하지 않습니다. |
| 문맥(Context) | 작업에 필요한 승인된 배경 정보입니다. | 외부 문서나 사용자 원문은 검토 전 문맥으로 승격하지 않습니다. |
| 입력 데이터(Input Data) | 처리 대상이 되는 사용자 입력 또는 자료입니다. | `<user_input>` 경계 안의 신뢰되지 않은 데이터로 취급합니다. |
| 출력 형식(Output Format) | 호출자가 기대하는 응답의 모양입니다. | JSON을 요구해도 소비 전에 별도 스키마 검증을 합니다. |
| 제약 조건(Constraint) | 허용값, 금지 형식, 길이처럼 작업 범위를 제한하는 규칙입니다. | Prompt 문구는 권한·접근 제어를 대체하지 않습니다. |
| 프롬프트 템플릿(Prompt Template) | 재사용 가능한 Prompt 구성 요소와 렌더링 규칙입니다. | 서비스 소유 섹션을 입력 데이터보다 먼저 고정합니다. |
| 역할 프롬프트(Role Prompt) | 모델이 맡을 업무 관점을 설명하는 서비스 설정입니다. | 역할 이름은 인증·권한 부여가 아니며 사용자 입력으로 만들지 않습니다. |

## 예시와 출력 계약

| 용어 | 정의 | 이 권에서의 경계 |
|---|---|---|
| 제로샷(Zero-shot) | 시연 예시 없이 새 입력을 처리하도록 요청하는 방식입니다. | 예시 수가 0개라는 계약을 검사합니다. |
| 원샷(One-shot) | 검토된 시연 예시 하나를 포함하는 방식입니다. | 예시는 새 사용자 입력과 분리된 서비스 소유 데이터입니다. |
| 퓨샷(Few-shot) | 두 개 이상의 검토된 시연 예시를 포함하는 방식입니다. | 예시 개수와 순서는 변경 검토 대상입니다. |
| 시연 예시(Demonstration) | 입력과 기대 출력을 보여 주는 검토된 예시입니다. | 실제 고객 원문이나 비밀값을 사용하지 않습니다. |
| 구조화된 출력(Structured Output) | 프로그램이 읽을 필드와 타입을 약속한 응답 형태입니다. | 자연어처럼 보이는 응답도 검증 전에는 신뢰하지 않습니다. |
| JSON 출력(JSON Output) | JSON 객체를 사용하는 구조화된 출력 방식입니다. | JSON 문법만이 아니라 필수 키·허용값·추가 키를 검사합니다. |
| 스키마(Schema) | 필드, 타입, 길이, 허용값을 기계적으로 검사하는 계약입니다. | 유효하지 않은 값을 추측해 보정하지 않고 실패로 처리합니다. |
| 실패 닫힘(Fail Closed) | 계약 위반 시 후속 처리를 중단하는 방식입니다. | 실패한 모델 문자열을 Tool 인자나 업무 처리로 넘기지 않습니다. |

## 추론·입력 안전 경계

| 용어 | 정의 | 이 권에서의 경계 |
|---|---|---|
| ReAct | 행동(Action)과 관찰(Observation)을 반복해 작업을 구성하는 개념입니다. | 이 권은 Tool을 실행하지 않고 공개 결과 계약만 다룹니다. |
| 연쇄 추론(Chain of Thought, CoT) | 문제 풀이 과정의 상세한 내부 추론입니다. | 내부 추론을 요구·저장하지 않고 검증 가능한 결론과 짧은 근거 요약을 사용합니다. |
| Prompt Injection | 입력 데이터가 서비스 지시를 무시하거나 비밀·권한을 요구하도록 유도하는 공격입니다. | 입력 경계, 형식 검증, 위험 신호, 권한 통제를 함께 적용합니다. |
| 신뢰 경계(Trust Boundary) | 서비스 소유 정책과 신뢰되지 않은 외부 데이터를 구분하는 지점입니다. | 사용자 입력과 외부 문서는 데이터로 표시하고 정책보다 뒤에 둡니다. |
| 입력 검증(Input Validation) | 빈 값, 길이, NUL 문자 같은 형식 오류를 모델 호출 전 검사하는 과정입니다. | 위험 신호 평가와 별개로 실패 닫힘으로 처리합니다. |
| 위험 신호(Risk Signal) | Injection 가능성을 알려 주는 문구 기반 보조 지표입니다. | 신호 자체는 권한 통제를 대체하지 않습니다. 인증과 Tool allowlist도 별도로 적용합니다. |

## 변경 검토와 테스트

| 용어 | 정의 | 이 권에서의 경계 |
|---|---|---|
| Prompt Versioning | 버전 ID와 변경 사유로 Prompt 변경을 추적하는 방법입니다. | 같은 고정 데이터셋으로 버전별 결과를 비교합니다. |
| Prompt 테스트(Prompt Testing) | Prompt 계약과 기대 결과를 반복 확인하는 테스트입니다. | 모델 호출 대신 고정 교육용 기록과 단위 테스트를 사용합니다. |
| 테스트 fixture | 테스트를 위해 검토·고정한 입력, 기대값, 태그 데이터입니다. | 실제 고객 데이터, API 키, 비공개 문서를 넣지 않습니다. |
| 회귀 검토(Regression Review) | 변경 전후에 같은 사례를 비교해 계약이 깨졌는지 확인하는 과정입니다. | 실패 ID를 기록하고 자동 보정이나 자동 배포로 연결하지 않습니다. |
| 사람 검토 후보(Release Candidate) | 고정 계약을 통과해 추가 검토 대상으로 표시된 상태입니다. | Tool 실행, 권한 부여, 데이터 전송, 배포 승인이 아닙니다. |

- [ ] 다섯 Prompt 구성 요소의 책임을 설명할 수 있다.
- [ ] zero-shot, one-shot, few-shot의 예시 계약 차이를 설명할 수 있다.
- [ ] JSON 출력 요구와 스키마 검증의 차이를 설명할 수 있다.
- [ ] Prompt Injection 위험 신호가 권한 통제를 대체하지 않음을 설명할 수 있다.
- [ ] 고정 fixture와 실패 ID로 Prompt 변경을 검토할 수 있다.
